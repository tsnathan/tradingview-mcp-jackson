# TradingView MCP — Claude Instructions

68 tools for reading and controlling a live TradingView Desktop chart via CDP (port 9222).

## Decision Tree — Which Tool When

### "What's on my chart right now?"
1. `chart_get_state` → symbol, timeframe, chart type, list of all indicators with entity IDs
2. `data_get_study_values` → current numeric values from all visible indicators (RSI, MACD, BBands, EMAs, etc.)
3. `quote_get` → real-time price, OHLC, volume for current symbol

### "What levels/lines/labels are showing?"
Custom Pine indicators draw with `line.new()`, `label.new()`, `table.new()`, `box.new()`. These are invisible to normal data tools. Use:

1. `data_get_pine_lines` → horizontal price levels drawn by indicators (deduplicated, sorted high→low)
2. `data_get_pine_labels` → text annotations with prices (e.g., "PDH 24550", "Bias Long ✓")
3. `data_get_pine_tables` → table data formatted as rows (e.g., session stats, analytics dashboards)
4. `data_get_pine_boxes` → price zones / ranges as {high, low} pairs

Use `study_filter` parameter to target a specific indicator by name substring (e.g., `study_filter: "Profiler"`).

### "Give me price data"
- `data_get_ohlcv` with `summary: true` → compact stats (high, low, range, change%, avg volume, last 5 bars)
- `data_get_ohlcv` without summary → all bars (use `count` to limit, default 100)
- `quote_get` → single latest price snapshot

### "Analyze my chart" (full report workflow)
1. `quote_get` → current price
2. `data_get_study_values` → all indicator readings
3. `data_get_pine_lines` → key price levels from custom indicators
4. `data_get_pine_labels` → labeled levels with context (e.g., "Settlement", "ASN O/U")
5. `data_get_pine_tables` → session stats, analytics tables
6. `data_get_ohlcv` with `summary: true` → price action summary
7. `capture_screenshot` → visual confirmation

### "Change the chart"
- `chart_set_symbol` → switch ticker (e.g., "AAPL", "ES1!", "NYMEX:CL1!")
- `chart_set_timeframe` → switch resolution (e.g., "1", "5", "15", "60", "D", "W")
- `chart_set_type` → switch chart style (Candles, HeikinAshi, Line, Area, Renko, etc.)
- `chart_manage_indicator` → add or remove studies (use full name: "Relative Strength Index", not "RSI")
- `chart_scroll_to_date` → jump to a date (ISO format: "2025-01-15")
- `chart_set_visible_range` → zoom to exact date range (unix timestamps)

### "Work on Pine Script"
1. `pine_set_source` → inject code into editor
2. `pine_smart_compile` → compile with auto-detection + error check
3. `pine_get_errors` → read compilation errors
4. `pine_get_console` → read log.info() output
5. `pine_get_source` → read current code back (WARNING: can be very large for complex scripts)
6. `pine_save` → save to TradingView cloud
7. `pine_new` → create blank indicator/strategy/library
8. `pine_open` → load a saved script by name

### "Practice trading with replay"
1. `replay_start` with `date: "2025-03-01"` → enter replay mode
2. `replay_step` → advance one bar
3. `replay_autoplay` → auto-advance (set speed with `speed` param in ms)
4. `replay_trade` with `action: "buy"/"sell"/"close"` → execute trades
5. `replay_status` → check position, P&L, current date
6. `replay_stop` → return to realtime

### "Screen multiple symbols"
- `batch_run` with `symbols: ["ES1!", "NQ1!", "YM1!"]` and `action: "screenshot"` or `"get_ohlcv"`

### "Draw on the chart"
- `draw_shape` → horizontal_line, trend_line, rectangle, text (pass point + optional point2)
- `draw_list` → see what's drawn
- `draw_remove_one` → remove by ID
- `draw_clear` → remove all

### "Manage alerts"
- `alert_create` → set price alert (condition: "crossing", "greater_than", "less_than")
- `alert_list` → view active alerts
- `alert_delete` → remove alerts

### "Navigate the UI"
- `ui_open_panel` → open/close pine-editor, strategy-tester, watchlist, alerts, trading
- `ui_click` → click buttons by aria-label, text, or data-name
- `layout_switch` → load a saved layout by name
- `ui_fullscreen` → toggle fullscreen
- `capture_screenshot` → take a screenshot (regions: "full", "chart", "strategy_tester")

### "TradingView isn't running"
- `tv_launch` → auto-detect and launch TradingView with CDP on Mac/Win/Linux
- `tv_health_check` → verify connection is working

### "None of the tv_*/chart_*/data_* tools are available this session"
CDP connectivity and MCP tool registration are two independent things — don't assume one implies the other:

1. Check CDP is actually up: `Invoke-WebRequest http://127.0.0.1:9222/json/version` (PowerShell) — a 200 with a TradingView user-agent means the debug port is live, regardless of whether any MCP tools are loaded.
2. Check the server is actually registered where Claude Code reads it: `~/.claude.json` → `projects["c:/Users/tsnat/tradingview-mcp-jackson"].mcpServers` must have a `tradingview` entry with `args` pointing at the absolute path to this repo's `src/server.js`. Note the project key uses forward slashes and a lowercase drive letter — looking it up with the backslash/uppercase form (`C:\Users\...`) will silently miss it. `~/.claude/.mcp.json` (a different, sibling path — `.claude` folder, not `.claude.json` file) has been found orphaned/unread in this setup before; don't trust it as the source of truth without verifying against `~/.claude.json` first.
3. If both of the above are fine but the tools still aren't showing up, the MCP server was registered/edited **after** the current Claude Code session started — it only loads config at startup. Restart Claude Code (quit and reopen), then confirm with `tv_health_check`.

## Context Management Rules

These tools can return large payloads. Follow these rules to avoid context bloat:

1. **Always use `summary: true` on `data_get_ohlcv`** unless you specifically need individual bars
2. **Always use `study_filter`** on pine tools when you know which indicator you want — don't scan all studies unnecessarily
3. **Never use `verbose: true`** on pine tools unless the user specifically asks for raw drawing data with IDs/colors
4. **Avoid calling `pine_get_source`** on complex scripts — it can return 200KB+. Only read if you need to edit the code.
5. **Avoid calling `data_get_indicator`** on protected/encrypted indicators — their inputs are encoded blobs. Use `data_get_study_values` instead for current values.
6. **Use `capture_screenshot`** for visual context instead of pulling large datasets — a screenshot is ~300KB but gives you the full visual picture
7. **Call `chart_get_state` once** at the start to get entity IDs, then reference them — don't re-call repeatedly
8. **Cap your OHLCV requests** — `count: 20` for quick analysis, `count: 100` for deeper work, `count: 500` only when specifically needed

## Tool Conventions

- All tools return `{ success: true/false, ... }`
- Entity IDs (from `chart_get_state`) are session-specific — don't cache across sessions
- Pine indicators must be **visible** on chart for pine graphics tools to read their data
- `chart_manage_indicator` requires **full indicator names**: "Relative Strength Index" not "RSI", "Moving Average Exponential" not "EMA", "Bollinger Bands" not "BB"
- Screenshots save to `screenshots/` directory with timestamps
- OHLCV capped at 500 bars, trades at 20 per request
- Pine labels capped at 50 per study by default (pass `max_labels` to override)

## Git Hygiene: check for uncommitted work before building on top of it

Before starting a new code change, run `git status`. If the working tree already carries
uncommitted changes that look like a **completed** prior feature — not the scratch/in-progress
state of the task at hand — surface it to the user and ask whether to commit before proceeding.
Don't silently build a new feature on top of an unrelated, already-finished one that just never
got committed.

**Why this rule exists (2026-08-05):** three separate finished feature builds — `accounts.js`
equity/alloc sizing, `sim_templates.js` plus the capacity-sweep expectancy pivot, and their
dashboard/server wiring — had accumulated uncommitted across earlier sessions, undetected because
nothing ever checked. A fourth feature (the Current Signal today-only-entries/exits fix) was then
built on top of that same uncommitted pile in a later session, without ever checking `git status`
first. When the user eventually asked to commit "one commit per feature build," separating four
entangled features required hand-splitting interleaved diff hunks inside `dashboard/index.html`
and `scripts/serve_signal_status.js` (built back-to-back with no commit between them, so their
hunks for two different features were interleaved within single 3-line-context blocks), plus
reconstructing `CLAUDE.md`'s own uncommitted section boundaries by string-slicing the file to work
out which paragraphs belonged to which feature. All of that forensic reconstruction — and its real
risk of a wrong split — is avoided entirely by noticing the pile at the *start* of a session
instead of untangling it at the end.

- **This is a detect-and-ask rule, not an auto-commit rule.** Per this project's standing
  instruction, commits happen only when the user asks for one. The fix is to flag pending
  uncommitted work early and let the user decide — commit now, commit later, or explicitly proceed
  on top of it — never to commit unprompted.
- **A `git status` (and `git diff --stat` if anything is listed) costs nothing and catches this
  before it compounds.** The four-feature pile above was avoidable at any of three earlier session
  starts, not only the first one — the cost of the check is the same regardless of how large the
  pile has already grown, but the cost of skipping it compounds with every additional feature.
- **"Looks like a completed feature" is the bar, not "any diff exists."** Mid-task state you are
  actively iterating on inside the current conversation is not what this is about. This is about
  uncommitted work from a *previous*, already-finished task still sitting untouched when a new,
  unrelated task begins.

## Automated Signal Scan — Status & Gotchas

This project also runs separate Windows-scheduled jobs independent of interactive MCP tool use: `TradingViewSignalScan15m` (every 15 min, the scan), `TVWatchdog` (every 5 min, CDP recovery), `TVDashboardWatchdog` (every 5 min plus at logon, keeps the dashboard server alive) and `TVMcpCleanup` (daily 4:00 AM, reaps orphaned MCP `server.js` processes — see "Never launch the MCP server from a shell" below). Full operational docs (how to suspend/resume, holiday list, desktop toggle shortcut) live in `USER_GUIDE.md`. Things worth knowing if you're asked to debug it:

1. **Two separate "off switches" exist and both must be checked.** The Windows Task Scheduler task can be Enabled while `rules.json` → `schedule.disabled: true` still silently no-ops every run ("Scheduled scanning disabled"). Always check both — `Get-ScheduledTaskInfo -TaskName TradingViewSignalScan15m` for the task, and `rules.json`'s `schedule.disabled` for the config gate.
2. **The dashboard server does not hot-reload code.** If you edit `src/core/morning.js` (or anything it imports) while `scripts/serve_signal_status.js` is already running, the running process keeps executing the *old* in-memory code until it's restarted. Compare the server process's start time (`Get-CimInstance Win32_Process -Filter "Name='node.exe'"`) against the file's last-write time before trusting a scan result you just triggered.
3. **A third, silent off-switch: `DisallowStartIfOnBatteries`.** `TradingViewSignalScan15m`'s task XML (`schtasks /query /tn TradingViewSignalScan15m /xml`) sets `DisallowStartIfOnBatteries=true` / `StopIfGoingOnBatteries=true`. On battery power, Task Scheduler silently refuses to launch each trigger — `State` stays `Ready`, `NextRunTime` keeps advancing normally, and nothing is logged anywhere (the `Microsoft-Windows-TaskScheduler/Operational` event log is disabled on this machine), so it looks identical to "everything is fine" from a glance at the task. The tell is `Get-ScheduledTaskInfo`'s `NumberOfMissedRuns` (nonzero and climbing) alongside `LastRunTime` stuck hours/days in the past despite being well inside market hours — cross-check with `Get-CimInstance Win32_Battery | Select BatteryStatus,EstimatedChargeRemaining` (`BatteryStatus: 1` = discharging). Found live 2026-08-05: laptop unplugged at 30% charge, task hadn't fired since the prior afternoon (6 missed runs and counting), `signal-scan.log`/status files frozen since. Fix is to plug in — no config change needed unless the task should also run untethered, which would mean removing `DisallowStartIfOnBatteries`.
4. **A fourth, and the least visible: an expired trigger. `State: Ready` does not mean a task is still scheduled.** Found 2026-08-05 while fixing the dashboard supervision below: `TVWatchdog` had not run since **2026-04-24** — three and a half months — while reporting `State: Ready`, `LastTaskResult: 0` and `NumberOfMissedRuns: 0` the entire time. CDP recovery was simply absent, and `CLAUDE.md` itself still asserted it ran every 5 minutes. The cause was the trigger shape, not the script: a single one-shot `TimeTrigger` whose `<Repetition>` carried `<Duration>P1D</Duration>` with `<StopAtDurationEnd>true</StopAtDurationEnd>`, so the 5-minute repetition ran for exactly one day past its 2026-04-23 `StartBoundary` and then stopped forever. **The only tell is an empty `NextRunTime`** — every other field looks healthy, and unlike the battery gate `NumberOfMissedRuns` does *not* climb, because a task with no upcoming run has nothing to miss. Both watchdogs now use a daily `CalendarTrigger` (`ScheduleByDay`/`DaysInterval` 1) with a 5-minute repetition scoped to `P1D`, which re-arms every day and cannot expire; use that shape for any new task rather than hanging an interval off a one-time trigger. When checking whether *any* scheduled job here is alive, read `NextRunTime`, not `State`.

### The dashboard server is supervised by `TVDashboardWatchdog` (2026-08-05)

`scripts/serve_signal_status.js` is the only long-lived process in this project — the scan job is a fresh process per run, so a crash there self-heals on the next trigger while a crash here is permanent until noticed by hand. It had been down since a `SyntaxError` crash on 08-04 16:28 (the offending edit was already fixed in the file by the time it was found, so nothing but the missing restart kept it down). `scripts/dashboard_watchdog.ps1` + `scripts/start_dashboard_detached.cmd` close that gap.

Six decisions in it that are easy to undo by accident:

- **Not gated on market hours or battery, unlike `tv_watchdog.ps1`.** The dashboard is a read-only local UI over already-collected data, equally useful at night, at weekends and unplugged. It is also deliberately excluded from the scan toggle shortcut and the `Disable-ScheduledTask` pair in `USER_GUIDE.md`: suspending scans means "stop driving TradingView and stop placing orders", not "take the dashboard offline".
- **The probe is `GET /api/scan-state`** — the only route that touches neither the filesystem nor `console.log`, so the health check cannot itself become the thing that stalls the server. **Known limitation: it cannot detect a *partially* wedged server** (one answering simple GETs while logging routes hang, the failure mode documented under `/api/restart` below). Detecting that would need a probe that logs, which is too invasive; a partial wedge is still a manual restart.
- **Kill-and-relaunch requires 3 consecutive bound-but-unresponsive checks (~15 min), and never touches a foreign process.** A slow request is far likelier than a wedged loop, and killing mid-write is worse than waiting another 5 minutes. Before killing, the owning PID's command line must contain `serve_signal_status` — otherwise it logs what owns port 3030 and does nothing, because killing whatever happens to hold a port is not a recovery strategy.
- **It retries forever instead of backing off after repeated failures.** This looks like a crash-loop guard is missing; it is the correct behaviour for exactly the incident that motivated it — the 08-04 syntax error was already fixed on disk, so an unconditional retry would have recovered on its own. After 3 failed launches it runs `node --check` on the server file and writes the syntax error into `dashboard-watchdog.log`, so the log names the cause rather than requiring two files to be correlated. That `node --check` captures stderr via a **temp file, not `2>&1`** — the script runs under `$ErrorActionPreference='Stop'`, where inline stderr redirection of a native exe becomes a `NativeCommandError` that can abort the run (same reason `run_signal_job.ps1` uses a temp file).
- **Launching goes through a `.cmd` file, and the redirect lives there.** Output must reach a file rather than an inherited pipe, for the reason spelled out under `/api/restart`. Building `cmd /c "node ... >> log 2>&1"` and handing it to `Start-Process` was tried first and **failed with `'"C"' is not recognized as an internal or external command` even with `/s`**, while a byte-identical standalone reproduction of the same call succeeded — cmd's outer-quote-stripping rules were not worth pinning down. A batch file has no quoting layer to get wrong and can be double-clicked to reproduce a startup failure exactly as the watchdog sees it. `Start-Process -RedirectStandardOutput` is not an option either: it truncates instead of appending, discarding crash history.
- **A healthy run logs nothing** (a quiet `dashboard-watchdog.log` means a quiet week), and it logs a line on recovery only. State lives in `status/dashboard-watchdog-state.json` (`hangCount`, `launchFailures`), mirroring `tv_watchdog.ps1`'s `status/watchdog-state.json`.

Verified 2026-08-05 end to end: killed the server and let **Task Scheduler** trigger the recovery (not a hand-run of the script, which uses a different invocation context) — detected down, relaunched, answering in ~2 s, `LastTaskResult: 0`, exactly one server instance, counters reset. The healthy path on the next 5-minute tick was a silent no-op with no duplicate spawn.

### A UTF-8 BOM on a JSON file blanks the whole dashboard, silently (2026-08-06)

User report: "the dashboard is not working as none of the open or previous signals are showing up" — Open Trades read "No open trades across the tracked time frames" and Current Signal was empty. **Nothing was wrong with the data**: `status/latest-signal-status.json` held all 86 open trades, 8 watchlist lines and `signalsFound: 6` the entire time. The file simply started with a UTF-8 BOM (`ef bb bf`), and `getStatus()` in `serve_signal_status.js` did `JSON.parse(readFileSync(f,'utf8'))` inside a `try { } catch { return defaultStatus() }`. `readFileSync` does not strip a BOM and `JSON.parse` throws on one, so every request silently served the empty default.

**The trap that costs the debugging cycle: `require()` strips a BOM and `readFileSync` does not.** A quick `node -e "require('./status/latest-signal-status.json')"` parses the file perfectly and reports all 86 trades, while the running server fails on the identical bytes. Check with `head -c 3 <file> | od -An -tx1` (`efbbbf` = BOM, `7b` = clean `{`) or `JSON.parse(readFileSync(...))` explicitly — never `require`.

- **PowerShell is the source, and it will happen again.** `Out-File`, `Set-Content` and `>` all emit a BOM by default on this machine (already noted in the PowerShell section of the tool docs). Anything that rewrites one of these files through PowerShell — a hand edit, a `ConvertTo-Json` round-trip, the backup/restore step this file recommends for live-data verification — adds one to a file Node wrote cleanly. The offending file was also reformatted in PowerShell's `ConvertTo-Json` style (4-space indent, `&` for `&`), which is the fingerprint to look for.
- **Fixed by stripping on READ, not by normalizing writes.** `src/json_file.js` (`stripBom`, `parseJsonText`, `readJsonFile`) is now the single reader, wired into all 33 `JSON.parse(readFileSync(...))` sites across `src/core/*` and `scripts/*`. A write-side fix cannot work: the BOM is introduced by writers outside this codebase.
- **`status/watchdog-state.json` and `status/dashboard-watchdog-state.json` legitimately carry BOMs** — the PowerShell watchdogs write them and PowerShell reads them, and `ConvertFrom-Json` tolerates a BOM. Confirmed nothing in Node reads either. Don't "fix" those.
- **The silent catch was the real defect, and the BOM fix does not cover the general case.** A truncated file (crash mid-write) still fails to parse. `getStatus()` now attaches `statusFileError` (message, path, size, mtime) and the dashboard renders a `#status-file-error` banner saying the cards are empty *because the file is unreadable*, not because the market is quiet. Without it, corruption and a genuinely quiet scan render identically — which is exactly why this went unnoticed.
- **It self-heals on the next scheduled scan**, which rewrites the file from Node with no BOM. So a dashboard that fixes itself 15 minutes later is not evidence the problem was imaginary.

Verified 2026-08-06: the API went from serving an empty default to all 86 open trades / 8 lines / 8 prior-signal groups on the real file; re-injecting the BOM into the live file still served 86 (reader is tolerant); truncating it to 5 KB produced the `statusFileError` banner instead of a blank dashboard; the file was restored byte-identical (md5 match) and the next scheduled scan wrote a clean 7b-prefixed file with 109 open trades and `connectionError: false`. 232/232 unit tests pass (8 new in `tests/json_file.test.js`, wired into `test:unit`/`test:all`).

**Found alongside it: `run_signal_job.ps1` threw before logging, so failing scans left no trace.** The `if ($LASTEXITCODE -ne 0) { throw }` sat *above* the `Add-Content .\signal-scan.log` block, so the one run whose stderr you actually need — a failure — captured it into `$stderrOutput` and discarded it. Live symptom: the scan exited 1 while `signal-scan.log` showed nothing newer than the previous day, which is indistinguishable from "no scans have run." Now logs first (prefixing `EXIT <n>` on failure), then throws.

### Anything derived for the status file is computed at the WRITE CHOKEPOINT, never at a producer (2026-08-06)

`createDashboardStatus()` is the one function both status writers funnel through — `writeLatestStatus()` in `morning.js` and `writeStatus()` in `serve_signal_status.js`. **Any field derivable from the baseline alone must be computed there, not in whichever producer happened to need it first.** `writeLatestStatus()` replaces the *whole* file on every path, so a producer that omits the field silently erases a previous write's value.

**This has now bitten three times, identically**, which is why it is stated as a rule rather than another incident note:

| date | field | symptom |
|---|---|---|
| 2026-07-28 | `watchlist_sync` | Watchlist Symbols panel blank except for ~15 min a day |
| 2026-07-29 | `trade_log_orphans` | "No orphaned symbols detected" for the entire life of the feature |
| 2026-08-06 | `edge` / `edgeRank*` / `isNewEntry` | Edge/Org/New columns and the NEW badge blank on every skipped tick |

The 2026-08-06 instance: `runBrief()` ranked open trades, but the five skip/error paths in `runSignalJob()` (schedule disabled, outside hours, connection error, strategy mismatch, nothing due) did not — and a skipped tick fires far more often than a real 15-minute scan, so it overwrote the ranked rows within minutes of every scan. `rankOpenTradesForStatus()` now has **exactly one call site, inside `createDashboardStatus()`**, and must keep exactly one. Adding a call at a producer instead re-opens this for whichever producer is added next.

- **The first two fixes patched the instance, not the class**, each adding the computation to one more path. That is why there was a third. Prefer moving the derivation to the chokepoint over adding a call at a new site.
- **Diagnostic**: if a dashboard field is populated right after a scan and empty a few minutes later, this is the shape. Check whether the last write was a skip (`skipped: true` in `status/latest-signal-status.json`), not whether the producing code is correct — it usually is.
- **Guarded by tests now**: `tests/dashboard_status.test.js` asserts the ranking fields survive a skipped write and a connection-error write, and `tests/edge_ranking.test.js` covers `attachOpenTradeRanks` (which had **zero** coverage — the direct reason a whole feature could blank without a red test). Both assert field *presence*, never scores, which come from the live trade log and would make the suite fail whenever real trading moves.

**Known remaining gap in this family (not yet fixed):** `buildOutsideHoursResult()` builds its own `watchlist_summary_lines` as bare `… | NO SIGNAL | <reason>` strings instead of calling `buildWatchlistSummaryLines()`. So on a tick where *nothing* is due, the Current Signal log loses today's OPEN/EXIT restatement that the "shows TODAY's entries until the ET rollover" section promises — the `skipped_due_schedule` branch that restates them is only reached when *some* watchlist is due. Same class, different field.

### Never launch the MCP server from a shell — it leaks a process that cannot exit (2026-08-06)

Ten `node server.js` processes from a single 2026-08-02 session were still resident four days later, holding 52 MB. Each had an equally orphaned `bash.exe` parent.

**The SDK's stdin handling is correct and does not need fixing** — measured: `node src/server.js < /dev/null` exits on its own in ~1 s. The leak needs a *live* stdin pipe. Running the server from a Bash tool call gives it the shell's still-open stdin, so the server waits on stdin while the shell waits on the server: a mutual deadlock nothing breaks from the inside. Confirmed on cleanup — every one of the ten shells exited by itself the instant its child was killed.

- **So don't run it from a shell.** The MCP server is started by the MCP client, which owns its lifetime. To smoke-test that it boots, redirect stdin (`node src/server.js < /dev/null`) and it exits by itself in a second.
- **`scripts/cleanup_stale_mcp.ps1`** is the reaper. **Dry run by default**; `-Apply` kills. It gates on *parentage*, not age — a properly-launched server is a child of the MCP client (`claude`), a leaked one is a child of a shell. **Age alone is not a safe predicate**: a real session can run all day, and killing a live server breaks it mid-conversation. It also skips anything matching `serve_signal_status`/`run_signal_job`, which are separately supervised.
- **`TVMcpCleanup`** runs it with `-Apply` daily at 4:00 AM. Daily `CalendarTrigger` (`ScheduleByDay`/`DaysInterval` 1) like the watchdogs, so it re-arms every day and cannot expire; `StartWhenAvailable` so a run missed while asleep fires on wake. Deliberately **not** battery-gated — a local process sweep has none of the reasons `tv_watchdog.ps1` has for `DisallowStartIfOnBatteries`, which is the documented silent off-switch on this machine. It is also **not** part of the scan toggle in `USER_GUIDE.md`: suspending scans means "stop driving TradingView", not "stop reclaiming leaked processes". A healthy run logs nothing, so a quiet `cleanup-stale-mcp.log` means a quiet week.
- Verified 2026-08-06 with a synthetic orphan: detected and killed it, while the live MCP server (parent `claude`) stayed unflagged **even with `-MinAgeHours 0`**, i.e. with the age gate fully removed and only the parent gate standing. The registered task was then force-run for real (`LastTaskResult: 0`), leaving the live MCP server, the railway MCP and the dashboard all untouched.
- These held no CDP connections, so this was wasted memory rather than a functional fault — but per the backfill hazards above, accumulated `node` processes have starved a later run of a usable CDP session before, so it is worth sweeping rather than ignoring.

### The holiday calendar is computed in Node and materialized for PowerShell (2026-08-05)

Holiday awareness is split across two languages, and the split is the whole story. `isMarketHoliday()` in `morning.js` **computes** the ten NYSE closures for any year (`getUsMarketHolidayDates`, Easter via the Anonymous Gregorian algorithm, weekend observance) and checks year−1/year/year+1 — so the Node scan gate has never needed a stored list and was already correct for 2027 and beyond. The two **PowerShell** gates (`run_signal_job.ps1`'s `Test-ShouldRunNow`, `tv_watchdog.ps1`'s `Test-MarketHours`) cannot run it and read a flat JSON list instead, which was `rules.json` → `market_hours.holidays`, hand-typed one year at a time and populated only through **2026-12-25**. Every day of 2027 would have read as a normal session to both.

`buildMarketHolidayCalendar()` / `syncMarketHolidayCalendar()` materialize the computed set into `status/market-holidays.json`; both PowerShell gates union it with `rules.json` via `Add-GeneratedHolidays`. `runSignalJob()` rolls it before any gate runs, and `scripts/roll_holidays.js` does it on demand (`--dry-run`, `--as-of yyyy-mm-dd`, `--years N`).

**A real bug found while building this, which had nothing to do with the rolling: `getObservedDate()` silently dropped a closure.** It computed the weekend shift as `formatDateString(year, month, day - 1)`, so New Year's Day on a **Saturday** — observed the preceding Friday, which falls in the *previous year* — produced `"YYYY-01-00"`. That is a well-formed string that can never equal a real market date, so it neither errored nor matched: the closure just vanished. Consequence, dated: **Friday 2027-12-31 read as a normal trading day to every gate, Node included.** Now shifted with `addDays()`. Verified: 2027 goes from 10 computed dates to 11 with `12-31` present, 2026 is unchanged, and 2028 legitimately shows 9 in-year dates because its New Year is attributed to 2027 (which is exactly why `isMarketHoliday` scans year±1).

Six decisions that are easy to undo by accident:

- **Do NOT reimplement the holiday rules in PowerShell.** Same reasoning as `sweet_spot.js` sharing its sweep with `sweep_portfolio_grid.mjs`: two implementations of one rule drift, and here the failure is silent and consequential — the gates would disagree about whether the market is open, with nothing indicating which had gone stale.
- **Always generate current year AND next year**, never "append next year once December's last holiday has passed." Two independent reasons: a cross-year observed closure is emitted by the *following* year's generator (2027-12-31 comes from `getUsMarketHolidayDates(2028)`), so a "2027 only" list misses a 2027 trading day; and it must not depend on the machine being awake during one particular week of December — asleep Dec 20 → Jan 5 still yields full coverage, verified via `--as-of`.
- **Never write an empty list.** An empty file reads as "no holidays" to both PowerShell gates, i.e. scanning and driving TradingView on a closed market — the dangerous direction. If generation yields nothing the previous good file is left untouched (`reason: "generated_empty"`, covered by a test).
- **Union with `rules.json`, never replace it.** `rules.json` holidays are now *only* ad-hoc closures no rule predicts (a national day of mourning). Preserving them matters because discarding one silently reopens a day the exchange had closed; unioning also means a missing/unreadable generated file degrades to the old behaviour instead of opening the gate. Corollary: *removing* a regular holiday from `rules.json` does not enable trading that day — the generator puts it back.
- **The roll is additive and wrapped in try/catch.** Nothing in `runSignalJob` reads the file (Node computes directly), so a failure costs a log line, never a scan. It writes only when contents change, so the 15-minute cadence pays one array comparison on all but a handful of runs per year.
- **`--as-of` forces a dry run.** Writing a calendar purged relative to a pretend date would drop holidays that have not actually happened, into a file feeding two live gates.

Half-days (1:00 PM ET closes) are deliberately not modelled — they are not holidays, and scans run to the normal 16:15 cutoff on those days. Verified 2026-08-05: 17 unit tests (`tests/market_holidays.test.js`, wired into `test:unit`/`test:all`), both PowerShell gates confirmed to see all 10 of 2027 by extracting their `Get-ScheduleGate` and calling it directly, and the scan-path wiring confirmed end to end by deleting the file and watching a run recreate it before the schedule gate short-circuited (live status file backed up and restored).

### Open-trade detection reliability (do not assume the Pine label is ground truth)

The strategy's on-chart status label (`Mode: Fast (active bar)\nLast signal: X\nBars since signal: N\nPosition: Flat/Long/Short`) is **not** fully reliable evidence of a currently open position:

- `Position: Flat` is safe to trust unconditionally (`strategy.position_size == 0` is unambiguous).
- `Position: Long`/`Short` is computed on the **active, still-forming bar** and can run one bar ahead of the confirmed Strategy Tester "List of Trades" — e.g. a trailing-stop exit already closed the position in the trade list, but the label hasn't reset because no new opposite signal has fired yet. Treating `Long`/`Short` alone as confirmation of an open trade produces false positives.
- Symbols can also switch exchange prefix between scans for the same instrument (e.g. `AMEX:AGQ` vs `BATS:AGQ`) — match by ticker (strip the prefix) + timeframe when checking continuity of an existing position, not by exact symbol string.

**Ground truth now comes from the internal API, not the DOM — for everything.** `getLatestTradeFromTester()` in `src/core/data.js` no longer scrapes the rendered "List of Trades" panel as its primary source — it calls `getStrategyPositionState()`, which reads the strategy's own `reportData()` object directly off the chart's internal JS model (`chart.model().model().dataSources()` → the data source whose name matches `/strategy/i` → `.reportData()`). This is the same object the Strategy Tester UI renders from, so `performance.all.totalOpenTrades` and `performance.openPL` are authoritative and instant — no virtualized-list scrolling, no text parsing. **The still-open trade is included in `reportData().trades[]` as the LAST element** (when `totalOpenTrades > 0`), carrying its real epoch-ms entry timestamp (`e.tm`), entry price, side (`e.tp`: "le"/"se"), and live MFE/MAE (`rn`/`dd`) — plus a *synthesized mark-to-market exit row* that the UI renders as Exit "Open" (verified live 2026-07-23: `trades.length` 7 vs `performance.all.totalTrades` 6 with 1 open). Historical avg/max MFE/MAE (`getAllTradesExcursionStats`) is also computed from `trades[]` (`rn.p`/`dd.p` are *fractions* of position value — 0.038 = 3.8% — scale ×100 for the percent units the alert-level math uses). The DOM scrape (`getLatestTradeFromTesterDom` / `getAllTradesExcursionStatsDom`, both unexported) survives only as a full fallback when no strategy source can be found or matched internally at all — a `trade_source` of `"strategy_tester_dom"` in the status JSON is itself a red flag worth investigating.

Three non-obvious traps if you touch this code again:
- **Matching studies by name only, not by method presence.** `reportData`/`performance`/`ordersData` exist as methods on the generic Study base class too (confirmed live: a "Dividends" study matched this way) — filter candidates by `/strategy/i.test(name)` only, never `|| !!(s.reportData || ...)`.
- **Freshly-attached/just-switched studies can return a mid-recompute snapshot if read once, immediately.** `readStableStrategyReportData()` polls a few times (~350ms apart, bounded ~2s) and requires the trade-identity signature (open trade's entry time/price/qty, or last closed trade's entry+exit price/time) to match twice in a row before trusting it. `openPL` — and the open trade's synthesized *exit* row, which is mark-to-market and moves with every live bar — are deliberately excluded from that signature; comparing them would either false-negative on "stability" or force waiting out real market movement.
- **Never fabricate a missing entry time.** An earlier version substituted the scan timestamp when `entryTime` was null (`buildOpenTrades`'s `|| entry.scanned_at` fallback). That single fallback produced three simultaneous dashboard bugs: wrong entry dates on every open trade, silently dropped Current Signal/ntfy events (the recency gates parse null as epoch-0 → "not recent"), and unbounded accumulation of "open" rows all dated at scan time. If entry time is ever unknown again, it must surface as unknown — the recency gates excluding such rows is correct behavior, not a bug to patch around.

### "Signals Found" badge vs the Current Signal list disagreeing — fixed 2026-07-28

The dashboard's top badges (`Signals: N`, `Changed: N`) and the "Current Signal" list below them used to be built from **two different definitions of "signal"**, which could show a nonzero badge with nothing matching in the list. Root cause: `signals_found`/`changed_signals` (`runBrief()` in `morning.js`) counted an entry as a signal via `entry.signal?.hasSignal && hasSignalChanged(previous, entry.signal)` as a fallback whenever it wasn't a *recent* confirmed OPEN trade — and `entry.signal` is parsed from the strategy's on-chart label **text** (`evaluateSignalFromSnapshot`, around line 340), the same `Position: Long/Short` reading the section above already documents as unreliable/one-bar-ahead. `hasSignalChanged`'s price-comparison arm fires on ordinary price movement, so a position opened days ago with an active label could get counted as "changed" on nearly every scan with nothing new having actually happened. Verified live: 3 counted "signals" were `BATS:EWO`/`WTAI`/`EDC`, all 1–5 days old, none shown anywhere in the list — the list (`buildWatchlistSummaryLines`) only ever displayed *recent* (within ~4 bars, or same trading day) confirmed OPEN trades, correctly excluding them.

Fixed by making the counter match the list's own definition instead of the label-text path:
- `signalEntries` in `runBrief()` now only counts `trade.signal === 'OPEN'` or `'EXIT'` entries that are recent-bar-or-same-day, exactly `buildWatchlistSummaryLines`'s existing OPEN test, extended symmetrically to EXIT.
- EXIT needed a new field to do this correctly: `entry.trade.entryTime` on an EXIT is when the now-closed position originally *opened* (could be days earlier), not when it exited, so recency can't be judged from it. Added `exitTime` to the EXIT branch of `getStrategyPositionState()` in `data.js`, sourced from `reportData()`'s `lastClosedTrade.x.tm` (the same exit-epoch field `trade_log.js` already reads for the closed-trade log — see below). The DOM-scrape fallback path never populates it, so a DOM-sourced EXIT is simply never counted as recent rather than guessed at.
- `buildWatchlistSummaryLines` gained a parallel `recentExits` block and now emits `EXIT: SYMBOL | P&L: ... | AT: ...` rows alongside `OPEN: ...` rows — previously a same-day EXIT had **no display path at all** in this function, and the `createDashboardStatus()` fallback that was supposed to catch that case (`hasExitSignalLines`, checking `signalLines` for literal `SIGNAL: EXIT` text) was dead code: `formatSignalLine()` never actually emits that string (it maps a non-OPEN trade to its bias `direction` — LONG/SHORT/SIGNAL — never the word EXIT). `hasMeaningfulSummary`'s regex was extended to recognize the new `EXIT: \w` lines too.

Verified live post-fix on `Swing 15m`: badge read `Signals: 3, Changed: 0`, and the list showed exactly 3 `EXIT:` rows (`URTY`/`TNA`/`RY`, all same-day) — `Changed: 0` correctly reflects that these exits were already recorded as seen in an earlier scan today, not that nothing happened. This is cosmetic-only to fix — the ntfy push and trade-webhook auto-send paths already independently required `trade.signal === 'OPEN'` *and* same-trading-day (real ground truth) before this change, so nothing was ever mis-notified or mis-executed by the old counting logic; only the badge/list display disagreed.

### The Current Signal log shows TODAY's entries and TODAY's exits, until the ET rollover (2026-08-05)

User requirement: "both entry and exit for today should appear in current signal until the next day rollover." The log answers *what happened today*; the Open Trades table stays the full holdings view. A watchlist with no activity today renders a bare `WAITING FOR NEXT … BAR`, by design.

Reported as "after the 15m scan the open pos are dropped" — three same-day `Swing 30m` entries (`SGHC`, `CVE`, `SHO`) visible in the Prior Signals table but absent from the Current Signal block. **Two independent causes, and the first one is the trap worth remembering.**

**Cause 1 was a stale dashboard process, not a filter bug — and it cost a debugging cycle.** The committed code already had the skipped-tick OPEN fallback with a same-day arm, and replaying that exact filter against the real status data returned `sameDay=true` for all three symbols. They *should* have rendered. The scan that wrote that file was an **off-cadence manual scan** (03:10:25 PM ET — the scheduled marks are :01/:16/:31/:46), run by a dashboard server instance older than the code on disk. Per the hot-reload note near the top of this file, `serve_signal_status.js` never re-reads `morning.js`. **Diagnostic rule: before treating a Current Signal anomaly as a display bug, check whether that status file was written by a scheduled scan (on-cadence, fresh process, always current code) or by a dashboard-triggered one (off-cadence, in-memory code of unknown age).** `updatedAt` not landing on a :01/:16/:31/:46 mark is the tell.

**Cause 2 was real: today's exits could not survive an intervening tick.** EXIT rows were built only from a *fresh* scan's results, and `baseline.signals` stored no exit timestamp at all (`entry_time`/`entry_price`/`net_pnl` only). A 2H exit rendered at 12:01 was gone by 12:16 when a 15m-only tick rewrote the block. `updateBaselineEntry` now persists `exit_time`/`exit_price`, `buildPriorSignalsByWatchlist` threads `exitTime` onto its rows, and `buildWatchlistSummaryLines` restates any exit whose `exitTime` falls on the scan's own ET date — in the `skipped_due_schedule` branch too, which previously rendered no exits whatsoever.

Seven things that are easy to undo by accident:

- **OPEN rows come from the `openTrades` list, NOT `priorSection.trades`.** `buildPriorSignalsByWatchlist`'s `keepOpenVisible` (~line 1121) relabels an OPEN as EXIT off `isSameOrPreviousTradingDay(entryTime, baselineUpdatedAt)`, so a stale `baselineUpdatedAt` can hide a genuinely same-day entry before the line builder ever sees it. Sourcing from `openTrades` removes that dependency and keeps the log and the Open Trades table on one source. The relabel itself was deliberately left alone — `priorSection.trades` feeds `buildOpenTrades` → `createExcursionAlerts` → webhook-sent gating, so changing what counts as OPEN there reaches the money path.
- **`exit_time` is nulled whenever the baseline record is OPEN.** A symbol that exits today and re-enters tomorrow would otherwise carry a stale exit and re-render as one. Covered by a test that exits then re-opens the same key.
- **`exit_time` is never carried forward from the previous record and never substituted with the scan timestamp.** The DOM-scrape fallback supplies no `exitTime`; null means the row simply does not restate, which is the same "a DOM-sourced EXIT is never treated as recent rather than guessed at" rule the rest of the file follows. Same family as the `scanned_at` entry-time bug documented above — an unknown must surface as unknown.
- **A relabelled stale OPEN carries `exitTime: null` and is excluded without a special case**, because it never actually exited. Pre-feature baseline records are null for the same reason and simply do not restate.
- **Fresh exits are merged OVER restated ones, deduped by bare ticker** (`normalizeSymbolForMatch`), so an exchange-prefix change between scans (`BATS:X` vs `AMEX:X` — the same drift `updateBaselineEntry`'s `altKey` match handles) cannot list one close twice. The fresh read wins because it carries this scan's real `netPnl`.
- **`entryTimeRaw` (ISO) is preferred over `entryTime` (ET display string).** The two pre-existing paths formatted this differently — fresh scan → `2026-08-05T15:15:00.000Z`, baseline fallback → `08/05/2026, 11:15:00 AM ET` — so which format you saw depended on whether the watchlist happened to be due. Now uniform.
- **The `recentOpenTrades`/`fallbackOpenTrades` paths survive as a degrade route** when no `openTrades` list is supplied, so a caller predating the parameter renders its previous output rather than nothing. Both real call sites pass it (`runBrief()`'s main path, and the partial-scan `onWatchlistComplete` writer, which passes its own `pTrades`).

**Migration:** baseline records written before this have no `exit_time`, so exits recorded earlier are not restatable. Self-heals on the next scan of each watchlist; no backfill. The `Signals: N` badge needed no change — it already counted today's OPEN/EXIT activity, so it now matches the list's definition exactly rather than merely being a subset of it.

Verified 2026-08-05 by replaying the real `status/latest-signal-status.json`: `Swing 30m` renders exactly `SGHC`/`CVE`/`SHO`, 45m renders `SBLK`, 1H renders `FRO`/`MUR`, 2H/3H/4H/1D render bare (no activity that day), and `CORT|15` (open since 08-03) is correctly absent. Exit threading was exercised end to end through `buildPriorSignalsByWatchlist` with a synthetic baseline: today's exit restates with its `EXIT SUMMARY`, yesterday's does not. 224/224 unit tests pass (8 new in `tests/morning_signals.test.js`).

### Strategy-identity guard (suspend + flag on mismatch, no auto-repair)

`checkStrategyIdentity()` in `src/core/morning.js` runs at the start of every `runSignalJob()` call (scheduled and manual/dashboard-triggered alike) and compares the chart's currently attached indicator names (`chart.getState().studies`) against `rules.json`'s `strategy` field. This exists because it's normal to swap in a different strategy on the chart temporarily (testing, comparison) — if that's still attached when a scan fires, every trade/signal read for that run would silently come from the wrong script with no visible error.

- On mismatch, scanning is **suspended immediately** for that run (same `skipped: true` early-exit path as `schedule.disabled`/outside-market-hours) and the mismatch is written to the status JSON as `strategy_mismatch` (`{ expected, found, detected_at }`), surfaced as a banner in `dashboard/index.html` (`#strategy-mismatch-banner`).
- **There is deliberately no auto-repair.** This was tried and removed: `chart_manage_indicator`'s `add` action calls TradingView's `createStudy(name)`, which can only add **public/built-in** indicators by exact name — it cannot restore a private saved script. Live-tested against this project's real configured strategy (`"Swing Profile Strategy [BigBeluga]"`, a private script customized with a trailing-stop exit): `createStudy` silently returned zero studies added. An auto-repair attempt here would either fail silently (as observed) or, worse, resolve to some unrelated public script sharing the same title. Suspend-and-flag is the only safe automatic behavior; restoring the correct indicator is a manual step.
- **To manually restore a private/custom strategy** (this account has more than one saved script titled `"Swing Profile Strategy [BigBeluga]"` — check `pine_list_scripts` and match by `modified` timestamp / ask the user which is current before picking one): `pine_open({ name })` only loads the source into the Pine Editor, it does **not** add it to the chart. You then have to click the editor's **"Add to chart"** button specifically — it's a distinct button (`title="Add to chart"`) from "Save script" and "Share your script with community", positioned just right of the editor's script-name dropdown. `pine_smart_compile`'s auto-button-detection can pick "Pine Save" instead if the editor thinks the script is unmodified — don't trust `study_added` from that tool for this flow; verify with a follow-up `chart_get_state` instead. Find the exact button coordinates via `ui_evaluate` (query buttons by `title` attribute in the top ~200px of the editor pane) rather than guessing screenshot coordinates, since the DOM button positions are stable even when screenshot pixel-scaling isn't.

### Closed-trade log (`src/core/trade_log.js`) — and why the Strategy Tester's headline stats lie

`scanSymbol()` calls `tradeLog.logClosedTrades()` on every scan, harvesting the full closed-trade history from `reportData().trades[]` into `trade-log/trades-<tf>.csv` (one file per timeframe, deduplicated by `ticker|tfLabel|entry_time_ms`). `scripts/backfill_trade_log.js` walks the whole watchlist universe for a one-time seed; `scripts/analyze_trade_log.js` reads it back.

**The reason this exists is a real measurement trap, not a nice-to-have.** `performance.all.profitFactor` and `percentProfitable` count only *closed* trades — a still-open loser contributes `$0` to `grossLoss`. Verified live on `BATS:WQTM|1D`: `profitFactor: 105.5`, `percentProfitable: 0.8`, `grossLoss: 34.79`, `numberOfLosingTrades: 1` — while that same symbol carried an open position at roughly **−$2,337**. Any strategy that exits winners and lets losers ride reads as near-perfect through this lens, and the distortion scales with how many positions are open. Never rank symbols or timeframes on `profitFactor`/`percentProfitable` straight from `reportData()`. Use either the CSV log (realized-only, honest denominator) or `netProfitPercent + openPLPercent` versus `maxStrategyDrawDownPercent`.

Trade-object field map (confirmed live 2026-07-24 on `AMEX:DUSL|60`), all of it now logged:

| Field | Meaning |
|---|---|
| `e` | entry — `{c: signal name, p: price, tm: epoch ms, b: bar index, tp: 'le'/'se'}` |
| `x` | exit — same shape, `tp: 'lx'/'sx'` |
| `q` | quantity · `v` position value at entry · `cm` commission |
| `tp` | trade profit `{v: USD, p: fraction}` · `cp` cumulative profit |
| `rn` | run-up / MFE `{v, p}` · `dd` drawdown / MAE `{v, p}` |

`e.c` / `x.c` are the strategy's own signal names (`"Swing Low"` → `"Flip Short"`) — the only available answer to "is the trailing stop actually firing, or does everything exit on a signal flip?". `x.b - e.b` gives exact bars held. All `.p` fields are **fractions** (0.0387 = 3.87%); `trade_log.js` scales them ×100 on write, so CSV percent columns are already in percent units.

Three invariants worth preserving if you touch this:
- **The open trade is never logged.** It's the last `trades[]` element when `totalOpenTrades > 0` and carries a synthesized mark-to-market exit row that moves with every bar — logging it would write a fabricated exit price, then never match on dedupe.
- **`rule_type` is part of the dedupe key, not just a column.** It records which exit-rule variant produced a trade (`flip-only`, `ts60`, `ts60-losing`, `sl-auto`, `sl12.0`, `ts60+sl-auto`, `unknown`), derived by `ruleTypeFromInputs()` from the strategy's **live input values** read off the chart — never from `rules.json`, because the toggles are set by hand on the chart and config would drift. If it were only a column, any trade a new rule did *not* alter would collide with its `flip-only` baseline row and be dropped on dedupe, leaving the comparison run holding only the trades that changed — the most biased possible sample. Because of this the logs are deliberately append-only across variants: one set of files holds every regime, separable by this column, and no separate directory per experiment is needed. Input titles carry leading spaces for indentation in TradingView's settings panel (`"    Bars in trade"` — confirmed live), so every lookup is trimmed; unreadable inputs yield `unknown` rather than a guess.
- **Nothing that varies with account state belongs in the key, and `existingKeys()` recomputes rather than reading the stored column.** Quantity used to be in the key (to separate margin-call rows sharing an entry timestamp). When `default_qty_value` went 100 → 95, sizing shifted qty on every trade, so every already-logged trade hashed differently and a single 4H watchlist rescan appended **285 duplicate rows** — verified identical trades, `pnl_pct` matching to 6 decimals, only qty differing by exactly 0.95. Exit time already separates margin calls without it (all 88 such rows have `entry_time_ms === exit_time_ms`, closing on their own entry bar), and all 1,485 rows were unique without qty. `existingKeys()` therefore derives each row's key from its own columns via the same `tradeKey()` the write path uses, so a future key-format change can never desync from stored rows or need a migration. Corollary worth its own line: **the CSV `trade_key` column is a convenience, not the source of truth for dedupe.**
- **Restart the dashboard server *before* scanning after touching `trade_log.js`, not after.** The server holds `trade_log.js` in memory (see the hot-reload note above). Normalizing the CSVs to a new key format and then triggering a scan against a server still running the old key code is the exact sequence that produced the 285 duplicates — the stale process wrote old-format keys against freshly normalized files, so every row missed. Scheduled scans are immune (`run_signal_job.js` is a fresh process each run); only the long-lived server is stale. Also note `/api/run-symbol-scan` seeds and sweeps the whole watchlist for that timeframe, not just the symbol named in the request.
- **`logClosedTrades()` verifies the chart's actual symbol/resolution before writing** (`verify: true` by default). A scheduled scan navigating the chart mid-call would otherwise file one symbol's trades under another's ticker, and bad rows are far harder to recover from than a skipped scan. Trades with no `e.tm` are skipped rather than given a substitute key.

**Every consumer of the log filters by variant, and pooling must stay opt-in.** `readAllTradeLogs({ ruleType })` is the chokepoint — `buildEdgeAnalysis`, `simulatePortfolio`/`sweepMaxPositions`, the `/api/edge-analysis` and `/api/portfolio-sim` endpoints (`?rule=<variant>`, `?rule=all`), the dashboard's Exit-rule chip row (shared state across both tabs, so they can never describe two strategies at once), and `analyze_trade_log.js` (`--rule`, `--rules`) all thread it through. Anything omitting the option pools every variant, which is right for inventory/coverage questions and wrong for every performance question; the default everywhere is therefore the **most-traded variant**, not `all`. `listRuleTypes()` is the inventory. One caveat that cannot be fixed inside the analysis layer: `openBySymbolTf` (open P&L, max drawdown) comes from `status/strategy-perf.json` written by the *current* chart state, so pairing it with a historical variant's closed trades mixes regimes — the resolved `ruleType` is surfaced in both tabs so the numbers are never unlabelled.

**Set exit-rule toggles in the settings dialog by hand — `indicator_set_inputs` does not reach the Pine engine, and the input properties are not proof of what ran.** Verified live 2026-07-25 on `AMEX:TMF|240`: `indicator_set_inputs({in_15:true})` (Time Stop) returned `updated_inputs:{in_15:true}`, and reading the property back through `metaInfo().inputs` → `properties().childs().inputs` confirmed `true` — while the strategy kept executing with it **false**. Proof it never took effect: 9 trades held past the 60-bar threshold (longest 236 bars) with zero `Time Stop` exits, and the script's own diagnostic label still reading `Exit rules: flip only`. A subsequent call setting it back to `false` matched nothing (`updated_inputs:{}`) even though the study resolved, so the state could not be reverted programmatically either. `indicators.js` uses the documented `study.getInputValues()`/`setInputValues()` pair, so this is not an obvious omission on our side. A symbol change — a full recompute — did not reconcile it.

Consequences, both important:
- **The on-chart diagnostic label is the only trustworthy record of the rule set in force**, because the script writes it during evaluation. `readAllTrades()` therefore also captures it (`runtimeExitRules`, parsed from `Exit rules: …`) and `reconcileRuleType()` compares the two on/off booleans against the property-derived rule type, downgrading to `unknown` with a console warning on disagreement rather than picking a side — a mislabelled variant silently merges two regimes inside what looks like a clean A/B sample, which nothing downstream could detect afterwards. Only the booleans are compared: the label prints the *effective* stop percent and cannot distinguish `sl-auto` from a manual level.
- Reading that label from the raw primitive map has **two traps**: `_primitivesDataById` is a `Map` (so `for..in` silently yields nothing), and the text is the **`t`** field — `text` exists only on the normalized shape the `data_get_pine_*` tools return. Both cost a debugging cycle here.

To confirm a toggle actually applied, read the label (`data_get_pine_labels`) and check the `Exit rules:` line — never the checkbox or the property.

Note that `flip-only` legitimately describes two builds: the pre-toggle script, and the toggled script with both switches off. Exit behaviour is identical, but the sizing fix that ships alongside the toggles (`default_qty_value` 100 → 95) makes post-deploy rows compound slightly slower than `pnl_pct` alone implies, and stops producing margin-call rows.

### Backfill hazards: leaked CDP sockets and partially-loaded history

Three failures found on 2026-07-25, each of which silently produced *plausible but wrong* data rather than an error:

- **`backfill_trade_log.js` leaked its CDP connection and never exited.** The script finished its walk, printed `Done.`, and the task runner reported exit 0 — but the open socket kept the event loop alive, so the process lived on as a zombie. Eight accumulated across one session; a later run then produced **no output at all** (not even its first log line) until they were killed, apparently starved of a usable CDP session. The script now calls `disconnect()` and then `finishProcess()` (`src/exit.js`) — **not** `process.exit()`, which is what it used to do; see "Never `process.exit()` straight after remote network I/O" below for why that pattern is unsafe and what replaced it. If a backfill ever appears to hang with an empty output file, check `Get-CimInstance Win32_Process -Filter "Name='node.exe'"` for stale `backfill_trade_log` processes first — and never run backfills in parallel, only sequentially.
- **Reads can land before TradingView finishes loading bars.** The strategy backtests whatever is loaded at that instant, so an early read returns a *truncated* history that writes as valid rows. Measured: the original daily seed captured `NVDA|1D` as **one trade spanning two weeks** where a later read returned **ten trades spanning seven years**; 11 of 26 daily tickers were short this way. This invalidated an entire variant comparison — the truncated baseline read as a strategy difference. `readStableTrades()` now polls (up to 6 × 900ms) until trade count and span endpoints repeat before writing, and sets `unstable_history` when they never settle. Daily needs far more wall-clock than intraday, so a flat sleep cannot be tuned once and trusted.
- **Suspect any variant comparison where position counts differ.** Under a pyramid variant each tranche is its own row in `trades[]`; under `flip-only` one position is one row. Comparing raw row counts conflates "more positions" with "more legs per position". Cross-check ticker sets *and* earliest-entry dates between variants before trusting any A/B result — a difference in either means you are measuring data capture, not strategy behaviour.

### Never `process.exit()` straight after remote network I/O (`src/exit.js`, 2026-08-05)

Forcing a process teardown while a remote HTTPS request is still settling aborts Node on Windows:

```
Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 94
```

exit code `0xC0000409` / `-1073740791`. **The command does its job first**, which is why this hid for so long: `tv pine check` printed a correct JSON result to stdout and *then* crashed, so anything reading stdout saw a perfect run and only the exit code was garbage. The single surface that noticed was `tests/cli.test.js`, which asserts `exitCode === 0` — it had two permanently red tests being written off as a flaky live-environment thing.

`finishProcess(code)` in `src/exit.js` is the replacement and the only sanctioned way for a CLI command or one-shot script to end: set `process.exitCode`, close CDP, let the event loop drain, and force-exit only via an `unref()`'d backstop timer. Used by `src/cli/router.js` (all seven exit sites) and `scripts/backfill_trade_log.js`.

Everything below was isolated by experiment, because the plausible explanations were all wrong:

| after `pine.check()` | exit | wall |
|---|---|---|
| `process.exit(0)` | crash 3/3 | ~1270 ms |
| set `exitCode`, drain naturally | **0** | **~720 ms** |
| `Connection: close` then `process.exit(0)` | crash 2/2 | ~1240 ms |

- **Draining is not a reluctant trade-off — it is ~500 ms *faster*.** The old code spent that time waiting on a teardown it was simultaneously aborting. Nothing hangs waiting on undici keep-alive, which was the reason to fear this change.
- **It is the forced exit, not socket pooling.** `Connection: close` still crashes.
- **Not stdin** (`pine check --file`, no stdin at all, crashes identically) and **not CDP** (`quote get`, `state`, `values`, `data strategy` all exit 0 in ~1 s). It needs the *remote HTTPS* request — `pine.check()` POSTs to `pine-facade.tradingview.com` with `fetch()`.
- **A localhost `fetch()` does NOT trigger it** — `http://localhost:9222/json/list` + `process.exit(1)` is clean 4/4, presumably because no DNS or TLS work lands on the libuv threadpool. This is why `pine_pull.js` / `pine_push.js` were **left alone**: their only `fetch` is to the local CDP port. A first pass "fixed" them anyway and introduced a real fall-through bug in the process (see the next bullet), then reverted.
- **`finishProcess()` returns; it does not terminate.** Swapping it into a bare guard clause like `if (!t) { ...; process.exit(1); }` silently changes control flow, because execution continues past it. Every call site must be a `return finishProcess(n)` or the last statement on its path.
- **The `unref()`'d backstop is the zombie guard, not decoration.** An open CDP socket keeps the loop alive forever — eight leaked `backfill_trade_log` processes once starved a later run of a usable CDP session (see the backfill hazards above). Verified: with a live non-`unref`'d interval holding the loop, the process force-exits at the ~2 s grace point carrying the requested code (0 → 0, 1 → 1); with CDP **and** a remote fetch both torn down together it drains on its own in ~1.1 s and never reaches the backstop.

Verified 2026-08-05: `tests/cli.test.js` 13/13 (was 11/13 with both `pine check` tests red), full `test:unit` 132/132, and `backfill_trade_log.js` exits 0 in 418 ms leaving no stale process.

### Portfolio simulation: merge pyramid tranches before allocating slots

`simulatePortfolio()` calls `mergePositionTranches()` first, grouping rows by ticker + timeframe + exit timestamp (every leg is closed by the same flip). Without it each tranche consumed its own slot, which understated fill rate by ~10 points and doubled per-symbol concentration; it also misread returns badly — one real 4H position had a base leg at **−2.08%** and its add at **+18.84%**, a net winner scored as one loser plus one winner. Returns are notional-weighted (`qty × entry price`).

The other half is `sizeFactor`: the Pine script sizes the base leg at `95/(1+addFrac)` so base+add together reach the same ~95% a flip-only entry uses, meaning a position whose add never fires deploys only `1/(1+addFrac)` of its allotment. Since adds fire on only ~15% of positions, ~85% carry a dead 20% cash reserve — measured as an 8-point drop in average deployed capital, and the dominant reason pyramid loses at portfolio level despite winning on per-trade expectancy on some timeframes. Crediting those positions as fully deployed would invent returns on money never at risk.

### Open Position Concurrency (Edge Analysis tab) — added 2026-07-29

User request: visualize least/average/max number of concurrently open positions over the trailing 1/2/3 months, grouped by timeframe. `computeOpenPositionConcurrency()` in `portfolio_sim.js` (new `/api/open-position-concurrency` endpoint, new "Open Position Concurrency" card in the Edge Analysis tab) answers this by sweeping a step function of "how many positions are open" through time and integrating it — min/max are the step function's extremes within the window, avg is **time-weighted** (a brief lull and an all-day stretch at the same level don't count equally, which a plain per-trade average would get wrong). Returns one row per timeframe plus an "All (pooled)" row combining every timeframe, for each of the 1/2/3-month windows in one response — no separate fetch per group, matching how the Timeframe Comparison table already shows every timeframe at once.

Two things reused deliberately rather than reinvented, both already established in `simulatePortfolio()` above:
- **Pyramid tranches are merged first** (`mergePositionTranches`, called directly since this lives in the same module) — an unmerged add-leg would inflate the concurrency count for what is really one logical position, the identical reasoning as slot allocation above.
- **Exit-rule variant is threaded through exactly like every other trade-log consumer** (`resolveRuleType()` at the API layer, defaulting to the most-traded variant, `?rule=all` to pool) — the dashboard card shares the Edge Analysis tab's existing rule-type chips/state (`loadConcurrency()` is called from inside `loadEdgeAnalysis()`, using the same `selectedRule`), so switching the exit-rule filter updates both sections together rather than needing a second, independently-stateful selector.

Same **closed-trades-only** limitation as `simulatePortfolio()`: a position still open right now has no `exit_time_ms` yet, so it's invisible to the sweep and the most recent slice of any window reads a little low relative to true live concurrency — this is a historical/descriptive view, not a live one (the dashboard's Open Trades count is the live figure), and the card's note text says so. Verified live against the real trade log (`flip-only` variant): min is genuinely 0 in every window, even pooled across all 8 timeframes and 400+ positions in the last month — real gaps exist where nothing is open across the whole book, not a bug in the sweep.

### Pyramid add trigger: fixed pooled level vs per-symbol MAE

The add trigger has two modes, selected by the `Add trigger` input, and they are different enough that the mode is part of `rule_type` (`pyr25` vs `pyr25mae75`) — pooling them would average two regimes with a 3× difference in how often the add ever fires.

- **Fixed per timeframe** (original) reuses `autoStopPct()`, which is the **95th percentile of _winners'_ adverse excursion pooled across all symbols** — a tail level, not an average, and not per-symbol. Measured at 15m, per-symbol average MAE spans **0.75% (EWO) to 5.87% (MEXX)**, so a flat 6% sits beyond the entire MAE distribution of half the watchlist: only **15.2%** of positions ever touched it. The other ~85% carried the add's idle 20% cash reserve for nothing, which is the mechanism behind pyramid's portfolio-level loss.
- **% of symbol MAE** tracks each symbol's own realised MAE in-script and triggers at `pyrMaePct%` of it (default 75) → **50.7%** fill rate at 15m.

The tracker (`pyrMaeSum`/`pyrMaeCount` in `src/strategy.pine`) deliberately does **not** use `strategy.closedtrades.max_drawdown_percent()`. Three reasons, each of which silently corrupts the statistic:
- A flip goes long→short **without `position_size` ever reading 0 on a bar boundary**, and flips are this strategy's dominant exit — detecting position close by `position_size == 0` misses nearly every trade. Closes are detected by **sign change**.
- Closed-trade indices list each pyramid **tranche** separately, so a stat built from them mixes short-lived add legs into what is meant to be a base-entry statistic. Tracking the live position sidesteps it.
- Excursion is measured from the position's **first** entry price, not `position_avg_price` — an add moves the average, and measuring against a yardstick the add itself shifted understates the very dip that triggered it.

**Result (15m, 2026-07-25): the mechanism worked and the strategy still didn't.** Add fill rate went 19.9% → 41.6% exactly as designed, and average deployed capital rose ~1-2 points — but matched-ticker expectancy was 1.50% vs flip-only's 1.60% (pyr25 was 1.48%), and portfolio CAGR/DD stayed at 1.8-6.6 against flip-only's 7.4-15.2 with roughly 3× the max drawdown. The diagnostic that explains it: positions where the add **fired** returned **+0.10%** while positions where it did **not** returned **+3.21%** (under `pyr25`: −1.25% vs +2.80%). The adaptive trigger genuinely improved the fired cohort by ~1.35 points — adding on a shallower dip catches recoverable ones rather than only the deep ones — but it also doubled how many positions joined that cohort, so the two effects cancel. Adding size on an adverse move means adding size to the worse-selected half of the book; no trigger level fixes that, because a shallow enough trigger to escape the selection just makes the add unconditional (i.e. leverage, not pyramiding). Treat the pyramid family as closed unless the entry rule itself changes.

Only positions closed *before* the current bar contribute, so there is no lookahead; until `pyrMaeMinTrades` (default 3) have closed, the fixed level is used and the label prints `WARMUP`. Warmup is not free: 15m symbols carry only 9-22 closed trades in the backtest window, so a high threshold leaves most of the sample running the fixed rule and dilutes the comparison. Note also that the level is measured under the pyramid regime it controls — self-consistent, but it drifts as trades close, so the label's printed level is the *final* one, not the one every trade saw.

### Ranking symbols: use expectancy, never CAGR/DD (measured, not assumed)

Walk-forward test on 2H+4H `flip-only` (rank each symbol on the first half of its own history, score it on the second half, Spearman rho, n≈48 symbol-halves):

| in-sample metric | rho vs OOS expectancy | | rho vs OOS expectancy |
|---|---|---|---|
| **expectancy** | **+0.381** | winRate | −0.018 |
| totalReturn | +0.225 | sharpe | −0.133 |
| perDay | +0.139 | **cagrDd** | **−0.145** |
| cagr | +0.092 | profitFactor | −0.168 |

Signs held across all 9 combinations of min-trades (6/8/10) × split point (0.4/0.5/0.6). **The ratio metrics rank slightly worse than random.** Max drawdown over 5-12 trades is essentially the worst single trade — near-pure noise that mean-reverts — so dividing by it ranks symbols by how lucky their worst trade was. Same mechanism for profit factor and Sharpe. cagrDd remains correct for a whole **portfolio** equity path (`renderPsSweep`'s slot sweep still uses it, rightly); it is unfit only for ranking individual symbols on a dozen trades.

Two consequences wired into the code, both easy to undo by accident:
- `buildEdgeAnalysis` sorts by `expectancyPct` with unrankable symbols (`RANK_MIN_TRADES` = 8) pushed to the bottom, and the dashboard's Keep/Watch/Drop verdict is a **within-timeframe percentile** (`expPercentile`), not an absolute cutoff. Expectancy scales hard with timeframe (15m ~1.7%/trade vs 4H ~7%), so any fixed threshold tags all fast rows weak and all slow rows strong.
- Both biases are real and opposite: cagrDd's old top-10 was almost entirely 15m-1H (one pick earned 0.57%/trade), while raw expectancy would return an all-4H/1D list. Only **2 of 20** symbols overlapped between the old and new top-20. Anything ranking across timeframes (the Portfolio Sim "top 20" picker) must therefore use `expPercentile`, not raw expectancy.

**Ranking is a filter, not a priority.** Walk-forward on 2H+4H: reordering which signal to take when several fire barely moved anything (13.7→13.7, 37.1→39.3, 108.4→121.4 CAGR), because simultaneous signals are rare. Dropping the bottom half by past expectancy moved a lot — but only when capacity-constrained: at **5 slots** (fill 39-50%) it helped in **5 of 5** split points (+6.1 to +91.7 CAGR); at **10 slots** (fill 66-80%) it was 3 of 5, twice materially negative (−8.7, −38.7). Selection only pays when you are turning signals away; above ~65% fill it mostly just removes trades. Check fill rate in Portfolio Sim before filtering anything. (CAGR *levels* in that test run 100-200% — short windows, heavy compounding — so trust the deltas, not the magnitudes.)

### Portfolio configuration: see `PORTFOLIO_RECKONER.md` (swept 2026-07-31)

Which timeframes to trade together and how many slots to run, measured over all 255 timeframe subsets × 7 slot counts, walk-forward validated. Regenerate with `node scripts/sweep_portfolio_grid.mjs`. Three things from it that are easy to get wrong and that any future analysis here has to respect:

- **`maxPositions` is the position-size divisor, not just a concurrency cap** — `size = portfolioValue / maxPositions`. Average CAGR is perfectly monotonic decreasing in slot count (3 → 118%, 30 → 28%) and so is drawdown (24.9% → 4.7%). Optimizing for max CAGR therefore always walks to the fewest slots; every in-sample winner across all three walk-forward splits landed at 3, the minimum offered. That is leverage, not edge — pick a risk point first, then optimize timeframes within it.
- **Slots are one pool shared across all selected timeframes, and a turned-away signal is skipped permanently, never queued.** Verified: at cap 3, 15m alone took 121 and 2h alone took 122, but together they took 164 rather than 243. `signalsTaken + signalsSkipped = signalsAvailable` exactly — when a slot frees it goes to whichever signal arrives next in time, not to a backlog.
- **In-sample CAGR is only weakly predictive of out-of-sample CAGR** (Spearman rho 0.522 / 0.185 / 0.284 across splits). Positive — unlike per-symbol cagrDd, which is negative — but far too unstable to justify picking the best of 1,785 combos. Recommendations there come from averaging a shortlist across every OOS window, not from the grid maximum.

Also fixed alongside this: the Portfolio Sim's **"Top 20 by CAGR/DD" button was mislabeled** — the code has ranked by `expPercentile` since the ranking work above, and only the label still named the metric this project measured as ranking *worse than random*. Relabeled "Top 20 by expectancy". No behavior change.

### Sweet Spot tab — `PORTFOLIO_RECKONER.md` as a live, on-demand view (2026-07-31)

User request: a tab for a sweet-spot finder based on the reckoner, with visualization and a lever to run the sweep on demand. `src/core/sweet_spot.js` (`runSweetSpotAnalysis()`) + `scripts/run_sweet_spot.js` + `/api/sweet-spot` (GET) and `/api/sweet-spot/run` (POST) + `pane-sweet`.

**The measurement moved into a shared module and `scripts/sweep_portfolio_grid.mjs` became a formatter over it.** Two implementations of the same sweep would drift, and the failure is silent in the worst way — the doc would assert one ordering while the tab showed another, with nothing indicating which had gone stale. Same principle as `/api/archive-orphans` shelling out to the real CLI rather than reimplementing its row-moving logic. The script's console output is unchanged apart from one added column.

Five decisions that are easy to undo by accident:

- **It runs in a child process, and is NOT behind `runExclusive`.** The full sweep is ~10,000 synchronous `simulatePortfolio()` calls (~3 min measured); in-process it would peg the server's event loop and make every other endpoint — including the webhook Close buttons — unresponsive for the duration. It has its own single-flight guard (`sweetSpotState`) because two concurrent sweeps would race to write the same file, *not* because a scan conflicts: it is read-only over the trade-log CSVs, and holding the scan lock for three minutes would block dashboard scans for no safety benefit. Verified live: a 409 on the second POST, and `/api/webhook-config` still answering mid-run.
- **A quick run carries the previous FULL run's grid forward rather than discarding it** (`gridFrom`), so a 30-second click cannot destroy a 3-minute result. It is never presented as part of the current run: the stale-warning box and every grid-derived card get their own provenance line naming the older run's timestamp and trade count. **Carried forward only when the exit-rule variant matches** — variants are different strategies, so a grid measured under one says nothing about another, and there dropping it is correct. Both paths verified against real files.
- **The result file is the only channel for results; stdout carries progress only.** `run_sweet_spot.js` emits throttled JSON progress lines (250 ms) that the server parses for the progress bar, and writes `status/sweet-spot.json` via temp-file + `renameSync` so a concurrent GET can never observe a half-written document. If the child dies mid-run the previous result is left intact.
- **Two ranks, because the reckoner's own "best all-round" call was made by eye.** The published `avg rank` column is CAGR-only; `rankOverall` is the mean of each config's CAGR rank and CAGR/DD rank within each window, and it drives the headline pick. Raw CAGR rewards concentration, which is the position-size divisor rather than an edge — a tab cannot eyeball the trade-off the way a human reading the table did. `worstRank` is exposed alongside because a strong average built from one dominant window and two poor ones is not a finding.
- **`expected` is carried alongside CAGR in every table** (shortlist, grid top, by-slot-count, by-timeframe-count) on user request. It is the non-compounding sibling fixed earlier the same day — mean per-trade return on the equity that funded it × trades/year. It earns its place here specifically because the reckoner's loudest caveat is "magnitudes are not forecasts — short windows with heavy compounding", and this is the column that shows how much of a headline number is the exponent: `15m+30m @ 3` reads 406.4% CAGR against 164.0% Expected. Measured result worth keeping: **the shortlist ordering is identical under both metrics**, and the slot-count monotonicity holds in Expected too — so neither is a compounding artifact. Averaged only over windows that produced a value, never over all windows, or a missing window would drag the mean down as if it had measured zero. Stored results predating the field render `—`, verified.
- **Sweet Spot and Portfolio Sim numbers do not match, by design — and the tab now says so.** User reported this for `15m+30m @ 3`: Sweet Spot 406.4% CAGR / 63% fill, Portfolio Sim 49.1% / 19%. Two differences, both large, measured by isolating each: **universe** (Sweet Spot always runs the Top-20-by-expectancy pick; the sim defaults to All — 44 tickers on 15m+30m, and that alone is 476.2% vs 49.1% over the same full history) and **window** (the shortlist scores only the out-of-sample stretch after each split, 3–6 months each, then averages three; the sim runs full history — all-symbols OOS-only is 235.4% vs 49.1%). A `→ Sim` button per shortlist row copies the timeframes, slot count and Top-20 universe across by **driving that tab's own controls** (never re-deriving the Top-20 rule, which must not exist twice), and the card states plainly that this fixes the universe difference but not the window one, so a lower CAGR there is the honest full-history number rather than a disagreement.
- **Staleness is reported, never acted on.** Two independent ways a stored result misleads — computed under a different exit-rule variant than the chips now show, or the trade log has grown since (`newTrades >= 50`) — each get a warn box. Nothing auto-reruns a multi-minute job.

Verified 2026-07-31, re-verified 2026-08-01 against the real trade log (4,402 `flip-only` trades). The full run (35s — see the memoization note below) reproduces every finding in `PORTFOLIO_RECKONER.md` — 1d's delta is by far the largest and negative (−56.2), slot count is monotonic in both CAGR and drawdown *on the grid average* (a single config can invert: `15m+2h` returns more at 5 slots than 3), timeframe count peaks at 2, walk-forward rho 0.475/0.130/0.241 (positive but unstable), `15m+30m @ 3` top of the shortlist and `15m+2h @ 5` last, and every in-sample winner landing at 3 slots. Magnitudes differ from the published table because the log has changed since it was written; the orderings match. The render path was exercised against the real payload under a DOM stub across 10 states (full, quick-with-carried-grid, quick-with-no-grid, never-run, stale, rule-mismatch, mid-run, failed, a walk-forward window with no viable combos, and pooled-rule) with no `undefined`/`NaN`/`[object Object]` reaching the page.

### Matched-window pass — configs were being compared on different markets (2026-08-01)

`computeMatchedWindow()` in `sweet_spot.js` (pass 4, `matchedWindow` in the result, "Matched-Window Check" card in the Sweet Spot tab, new section in `PORTFOLIO_RECKONER.md`). Passes 1-3 all score a config over **its own** union span, and logged history per timeframe ranges from **1d at 9.74y (starts 2016-11-03) down to 30m at 0.55y (starts 2026-01-12)** — so `15m+30m` and `all 8 TF` were never run over the same market, and any ordering between them was partly a statement about which years each one happened to cover. This pass fixes the calendar to the stretch where every shortlist timeframe has data and re-ranks there.

**Result: `15m+30m @ 3` survives the stricter test** — avg rank 1.17 with a *worst* finish of 2nd across six rolling starts; nothing else is close on stability (next best worst-rank is 6). It also settles two things the other passes could not: 3 slots beats 5 for the same pair on **every** axis (rank 1.17 vs 3.67, return 80.5% vs 64.3%, ret/DD 16.2 vs 10.4, not just raw return), and the **Top-20 filter only earns its keep at 3 slots** — fill is 58% there, inside the capacity-constrained regime where selection pays, against 81% at 5 slots where per "Ranking is a filter, not a priority" trimming mostly just removes trades.

Five decisions that are easy to undo by accident:

- **Ranked on TOTAL RETURN over the window, never CAGR.** The shared window is bounded by the youngest timeframe (0.55y here), and CAGR's `1/years` exponent inflates exactly that regime — the trap already documented under `expectedPct`. CAGR is still carried per row for continuity with the other tables; it just doesn't decide the ordering.
- **The universe is picked from data strictly BEFORE each window opens** (`topTickers(rows, n, { endMs: startMs })`). Picking over all history would leak the window's own outcome into the selection. When pre-window history can't rank 10 symbols it falls back to full-history picking and sets `lookahead: true` on that window, surfaced as a warn box — never silently substituted.
- **Rolling starts all share the same END date**, so they overlap heavily and are **not** independent samples. This is a consistency check on the ordering, not N experiments, and `worstRank` therefore carries as much weight as `avgRank` — a config that wins one window and finishes last in another has shown nothing. Both the card and the doc say so explicitly.
- **Runs in BOTH quick and full modes and is never carried forward.** It is ~66 simulations against the memoized trade log (~380ms for a whole quick run including it), the same order of cost as the shortlist pass quick mode already pays. Unlike `grid`/`walkForward` it is recomputed every run, so `run_sweet_spot.js`'s `gridFrom` carry-forward deliberately does not touch it — a stale matched window would be attributing the current log's ordering to an older measurement. A stored result predating this feature renders "re-run the sweep to compute it", verified.
- **Wrapped in try/catch, additive only.** A failure yields `{available:false, reason:"error"}` and costs a card, never the three passes above.

- **The gate is per (ticker, TIMEFRAME) and `simulatePortfolio`'s existing `tickers` option cannot express it.** `tickers` is ticker-level; measured, filtering by it changes *nothing* (all 133 logged tickers remain a member on some timeframe) while the pair filter removes 321 rows. - **Empty membership means "unknown", not "nothing is tradable"** — it gates nothing, matching `buildUniverse` and `findWatchlistOrphans`. A failed watchlist read must not silently empty every analysis on the dashboard. Same for an unreadable `rules.json`/baseline in `run_sweet_spot.js`'s `loadMembership()`.
- **Membership is part of a stored sweep's identity, exactly like the rule variant.** `run_sweet_spot.js`'s quick-run carry-forward now refuses to reuse a grid measured under a different membership setting (`sameUniverse`), because a gated and an ungated grid describe different universes and relabelling one as the other is the failure mode that whole file guards against. Verified live: the pre-feature stored grid was correctly dropped rather than carried.
- **`summarizeMembershipFilter()` is reported on every gated surface, never omitted.** A number that moved because six symbols left a watchlist looks identical to one that moved because the strategy changed; only the note distinguishes them. `?membership=off` on any analysis endpoint (and `--no-membership` on the sweep script) gives the unfiltered view, which is the correct lens for "what would this have returned historically".
- **`attachOpenTradeRanks`/`buildSymbolEdgeScores` on the SCAN path are deliberately left ungated.** They rank positions you currently hold, which is a different question from what to trade next — gating would blank the Edge score of a held position on a dropped pair, and per the portfolio-cap rules an unscored row is never flagged over-cap, so the cap would quietly stop seeing it. Symbol Lookup is ungated for the same reason: it is a direct "tell me about X" query, and a removed symbol vanishing from it would defeat the tool.

**This is survivorship filtering by construction, and it was measured rather than waved at.** Those trades genuinely happened while the symbol was scanned. Measured on the real log the bias is mild and does *not* flatter: excluded trades average 3.31%/trade against 3.74% for kept ones (+0.03pp on pooled expectancy), the per-timeframe tilt changes sign (1d and 4h get *worse* under the gate), and the 15m+30m@3 headline CAGR **drops** 49.1% → 45.9%. The exclusions are not random, though, so a gated and an ungated result are never directly comparable.

### Universe selection (`src/core/universe.js`) and paper runs (`src/core/paper_run.js`) — 2026-08-01

Built for a forward test of a `15m+30m` book at 3 or 5 slots, re-picking the universe monthly. Three measurements shaped the design and each is easy to undo by accident.

**The finding that motivated it: universe selection on 15m+30m cannot be backtested at all.** 30m's log begins 2026-01-12, so symbols only cross the 8-closed-trade ranking floor in the last few months. Sweeping the eligible-universe size at monthly walk-forward starts gives `0, 0, 0, 0, 1, 1, 1, 1, 1, 2, 4, 6, 18` — there is essentially no history in which a rankable universe existed. A paper run is the only instrument that can answer this, which is why the tab exists rather than another sweep.

**A trap found while measuring that, worth knowing anywhere `simulatePortfolio` is called: `tickers: []` does NOT mean "no symbols".** The filter is `if (tickers?.length)`, so an empty array skips filtering entirely and silently simulates the **whole** log. A first version of the walk-forward test passed empty universes and produced a confident, entirely fictitious table in which universe sizes 20/30/all were identical. Always guard the empty case at the call site.

**A forward universe must be gated on CURRENT watchlist membership — the trade log alone keeps ranking dropped symbols forever.** Found live 2026-08-01 when the user asked why KORU appeared in a 30m universe after removing it: `buildUniverse` ranked purely on trade-log history, so **3 of 15 picks (KORU, MU, EWY on 30m) were symbols no longer scanned on 30m**, and KORU was ranked #1 — the best slot in the book spent on a symbol that can never signal there again. `buildWatchlistMembership(rules, baseline)` builds per-(ticker, timeframe) membership and `buildUniverse({membership})` filters on it **before** percentiles are computed, so a stale pair cannot shift where the tradable ones rank. Four things this depends on:
- **`watchlistNames` must come from `rules.json`'s configured names, never `baseline.watchlists` directly.** The dead `"Swing 30min"` entry (superseded by `"Swing 30m"`) still holds 8 symbols including KORU, so a naive membership read passes KORU as a member and defeats the check entirely. Identical trap and identical fix to `findWatchlistOrphans`.
- **Stricter than the orphan check, deliberately.** Orphan detection is ticker-level and correctly does *not* flag KORU — it is genuinely still live on 3h. Being live somewhere does not make it eligible for a 30m slot.
- **Empty membership means "unknown", not "nothing is tradable"** (`membershipApplied: false`, no filtering) — the same reasoning that stops `findWatchlistOrphans` offering to archive the whole log. Verified: an empty map yields the ungated 15 picks, not zero.
- **This gate was originally scoped to FORWARD picks only** — historical analysis deliberately did not use it, because those trades genuinely happened while the symbol was scanned and excluding them imposes survivorship bias. **Superseded 2026-08-02 on user requirement**: every analysis surface is now gated by default (see "Every analysis surface is gated on active watchlist membership" above), which makes them all answer "what should I run next" rather than "what would this have returned". The bias was measured before making the switch and is mild and non-flattering, but it is real; `?membership=off` is the escape hatch on every analysis endpoint, not just this one. Verified live: gated 39 eligible / 7 stale excluded vs ungated 44.

Excluded pairs are returned as `excludedStale` and rendered rather than silently dropped — a deliberate removal and a watchlist that needs re-adding look identical once the row just disappears.

`buildUniverse()` differs from the dashboard's original Top-20 picker in three further measured ways:
- **Ranked WITHIN the traded timeframes.** The original took one timeframe per ticker across all eight, so a ticker could enter on its 4h record and then be traded on 15m/30m signals that were never ranked — visible live as greyed rows in the Portfolio Sim's universe table.
- **Blended with a pooled all-timeframe percentile** (default 50/50). A ticker's slow-timeframe expectancy predicts its fast-timeframe expectancy at **rho 0.686** — far stronger than expectancy predicts itself forward in time (~0.38) — so the pooled leg measures the same symbol quality on 3–5× the sample and damps churn. Selecting the top 20 on slow-timeframe data alone lifted mean fast expectancy from 1.75% to 2.24%. **This transfer figure is contemporaneous, not predictive**: it justifies pooling for a bigger sample, it is not itself an out-of-sample result. A ticker must still qualify on the traded timeframes to be eligible at all — the pooled leg only moves its position, or the defect above returns.
- **Hysteresis** (`HYSTERESIS` = 1.35). A month adds only ~5 (15m) / ~3 (30m) trades per symbol, and measured month-over-month churn is ~25% even on an all-history lookback. A held name survives until it falls outside `size × 1.35`, displacing only newcomers, never another held name. **Short lookbacks do not work here** — trailing 30 days leaves 0–4 eligible symbols and 90 days churns 60% per month; the default lookback is deliberately all history.

`replayPaperRun()` trades **one** live arm and replays the same realized signal stream through every slot count. Running two live arms would collide on the same symbols at one executor account and split capital for no extra information; fills are deterministic given signals and the cap, so the sweep is free. Four things to preserve:
- **It records nothing of its own.** `trade-log/*.csv` already holds every closed trade with entry/exit timestamps; a parallel recorder would be a second source of truth that could drift. This module is a *view* over the log restricted to the run's universe, timeframes and start date. Verified bit-identical to a direct `simulatePortfolio` call in the single-epoch case (finalEquity, winRate, profitFactor all match exactly).
- **`simulatePortfolio` returns aggregates, not the per-trade array** — there is no `result.taken`, only `signalsTaken`. Reconstruct win/loss totals from `winRate`/`avgWinUsd`/`avgLossUsd`, and note `avgLossUsd` is returned **negative**. A first version iterated `r.taken || []` and silently reported 0% win rate and infinite profit factor across every variant.
- **Open-trade rows carry the RAW resolution (`"120"`, `"30"`), not a label.** Comparing them against label-form timeframes (`"2h"`, `"30m"`) matches nothing — `openNow` read 0 with 10 positions genuinely open until this was routed through `timeframeLabel()`. Same class as the display-vs-raw entry-time bug documented above.
- **A universe re-pick APPENDS an epoch rather than replacing the list**, so the replay honours what was tradable at each point instead of applying today's picks retroactively. Epochs are simulated separately with equity chained, which force-closes a position open at a boundary; with median holds of ~2 days (15m) and ~4 days (30m) against monthly epochs this touches few positions and touches every slot variant identically, so the comparison stays fair. `committedAt` must be strictly after the previous epoch or the segment would be negative-length and vanish silently — enforced with a 400.

**What two months can and cannot establish, stated in the tab itself:** per-trade dispersion on 15m+30m is 3.96%, so ~30–50 closed positions leaves a 95% CI of ±1.1–1.4% against an expectancy of ~2–3%. That can establish "this is positive"; it cannot rank slot counts — and does not need to, since most of the 3-vs-5 difference is the deterministic size divisor. What the run genuinely tests is fill quality against logged prices, whether live signals match the log, and whether the freshly-rankable universe holds up. Same closed-trades-only limitation as everything else built on the log, reported as a warn box with the live open count rather than hidden.

### `readAllTradeLogs()` is memoized on file size+mtime (2026-07-31)

Was re-parsing 2 MB on every call — an Edge Analysis tab load (edge + concurrency + sim) paid it three times for ~500 ms of pure overhead, and parameter sweeps made it pathological. ### Hold period is calendar days, not bars — and always report median alongside mean

`edge_analysis.js` exposes `avgHoldDays`/`medianHoldDays` per symbol, per timeframe rollup, and pooled across the whole watchlist at the top level, all derived from `exit_time_ms - entry_time_ms`. Deliberately **not** based on `bars_held`: 60 bars is 15 hours at 15m and 60 calendar days at 1D, so a bar count answers a different question than "how long is capital tied up," which is the same question the portfolio simulator's time-weighted capital-utilization metric answers at the whole-portfolio level. Margin-call rows are left in, same as every other stat in `basicStats()` — they're a real (if degenerate) ~0-day holding, not filtered elsewhere in that function.

The distribution is right-skewed enough that mean alone misleads: on `flip-only|1D`, BE's winners average 64.9 days held against losers' 142.5 — no stop exists in the baseline, so losers ride far longer than winners, and a handful of those drag the mean well above the median. Always show both; the dashboard's `fmtHold()` switches units (hours under 1 day, days under 30, months beyond) because the range spans both ends across timeframes.

### `expectedPct`: CAGR's non-compounding sibling — added 2026-07-28

CAGR compounds the observed multiple to the power of `1/years`, where `years` is the calendar span from first entry to last exit (mostly idle time for a sparsely-traded symbol). Over a short or sparse span that exponent turns a modest run into a headline number the trade-by-trade record doesn't support — e.g. `KORU|3H` (flip-only) showed a CAGR of 3584.8% off 13 trades. The user's framing: "for a given timeframe, avg number of trades × a year factor will be a better measure" — i.e. use the symbol's own trade cadence, not compounding, to project a year.

`edge_analysis.js`'s `buildEdgeAnalysis()` now computes it per symbol as `expectancyPct * (365.25 / avgHoldDays)` — average return per trade × how many such trades would fit in a year back-to-back at this symbol's own average hold period. No compounding anywhere. Same `KORU|3H` row: CAGR 3584.8% vs Expected 422.4% — still a rich number, but one a reader can sanity-check against the 13 actual trades instead of an exponent. The two metrics are **not** a "toned down vs. real" pair — they can diverge in sign: `KORU|1D` showed CAGR ≈ −1% (a couple of bad losers crushed the compounded path) against Expected ≈ +47.6% (the average trade was solidly positive; Expected doesn't see path-dependency). Both numbers are real, they answer different questions — CAGR is the compounding-portfolio-equity lens, Expected is the trade-frequency lens — and the dashboard shows both side by side (Symbol Ranking table, Timeframe Comparison table, Symbol Lookup's per-timeframe stats) rather than picking one. `avgHoldDays == null` or `0` (no trades with a valid entry/exit pair) yields `expectedPct: null`, never a divide-by-zero.

### The Portfolio Sim's `expectedPct` was measuring simple annualized return — fixed 2026-07-31

`portfolio_sim.js` has its **own** `expectedPct`, unrelated to `edge_analysis.js`'s above, and it was wrong in two compounding ways. User caught it from the symptom: Expected 242.9% against CAGR 147.7% on a 15m+2h/5-slot run.

**It collapsed algebraically.** The form was `(expectancyUsd / capital) * tradesPerYear * 100` where `expectancyUsd = (gp - gl) / n`. Since every position closes, `gp - gl` **is** `finalEquity - capital`, so multiplying by `n/years` cancels `n` outright and leaves exactly `totalReturnPct / years` — simple annualized return, under a label promising a trade-frequency measure. Trade count did not enter the result at all. Verified bit-identical on three selections before the fix.

Consequence: **Expected > CAGR was structurally guaranteed, carrying zero information about the strategy.** By Bernoulli's inequality `(M−1)/y ≥ M^(1/y) − 1` for any profitable run with `y > 1` — confirmed at every slot count from 1 to 30 (ratio 1.28–1.93) — and it *inverted* below a year (30m alone, 0.55y: CAGR 173.7% vs Expected 134.2%). The ordering was reporting span length, not performance.

**It also mixed size regimes.** `size = portfolioValue / maxPositions`, so on a compounding path position size tracks equity — measured on that same run, the first fill was sized $20,000 and the last $112,060. Averaging *dollar* P&L across that and dividing by the **starting** capital annualizes late large-size trades against a small denominator.

Fixed by measuring each trade against the equity that funded it: `takenEntry` now carries `equityAtEntry` (the `portfolioValue` already computed at sizing time), and Expected is `mean((pnlUsd − commission) / equityAtEntry) × tradesPerYear`. Same run: **242.9% → 95.0%**, now correctly *below* CAGR (147.7%) — the right ordering for a linear-vs-compounded pair on positive returns, and it now holds sub-year too (30m: 103.1% vs 173.7%). `finalEquity` is unchanged at $562,920.71; this was measurement-only, the simulation itself was never wrong. Verified against an independently written replica of the fill loop that reproduces `finalEquity` to the cent.

Three things to preserve:
- **Commission is netted per trade here but not in `expectancyUsd`.** CAGR is already net of it via `finalEquity`, and the two sit side by side in the metric grid to be read against each other. `expectancyUsd` stays gross, unchanged, so nothing that consumed it shifted.
- **`equityAtEntry` must survive an eviction's rewrite.** `oracle-worst-final` overwrites `takenRef.pnlUsd`/`exitMs`, but the trade genuinely *was* funded at that equity regardless of how it ended, so the field is deliberately not touched there.
- **`expectancyPctOfEquity` is exported and shown next to the dollar expectancy** on the dashboard, because the dollar figure has the identical size-mixing defect wherever it's read.

**Second, separate trap this surfaced: `years` is the UNION span of the selected timeframes.** Logged history per timeframe ranges from 1d at 9.74y down to 30m at 0.55y, so selecting 1d+30m annualizes over 9.74 years a book in which 30m contributed 106 of 248 taken trades inside the final 0.55y. This is not an arithmetic error — the portfolio really did run that long — but it silently changes what CAGR and Expected describe. `timeframeSpans` (per-timeframe start/end/years/`coveragePct`, ascending by coverage) is now returned, and the dashboard raises a fourth warn-box when any selected timeframe covers under 80% of the simulated span. 15m+2h does *not* trigger it (97.6% / 100%) — the user's original hypothesis was that a short 15m history was distorting their run, and it wasn't; 15m has 1.86y against 2h's 1.91y. The <1y timeframe is 30m.

### Watchlist selection: "drop symbols with DD > X%" doesn't work — tested and rejected 2026-07-25

A per-symbol max-drawdown cap (e.g. "keep only DD < 30%, rank survivors by CAGR/DD") looks like a sensible risk screen. Walk-forward tested (rank on first half of each symbol's history, score the second half, 2H+4H `flip-only`) and it fails on both halves independently:

- **In-sample maxDD does not predict out-of-sample maxDD** (Spearman rho 0.082 — noise). A symbol's historical DD over 6-12 trades is mostly its single worst trade, same defect as ranking by CAGR/DD (see above).
- **It actively inverts on expectancy** (rho +0.495): the highest-DD quartile *outearned* the lowest-DD quartile out-of-sample on both timeframes (4H: Q1 0.7%→OOS 4.54% vs Q4 39.6%→OOS 11.38%). This is a momentum strategy on leveraged/volatile instruments — the volatility that produces the drawdown is the same volatility that produces the edge, so screening one out screens out the other. Concretely, a DD<30% cap on 4H removes `SOXL, PILL, MEXX, TNA, MIDU, AMDL` — average expectancy of the removed group (7.11%/trade) is *higher* than the kept group (4.96%/trade).
- **At portfolio level it loses on both axes it's meant to protect**: walk-forward at 10 slots, the filtered portfolio returned *less* CAGR *and* higher max drawdown than trading the full watchlist (4H: 60.8%/3.4% filtered vs 112.3%/2.2% unfiltered). Portfolio drawdown is driven by how many positions lose *simultaneously*, which a per-symbol screen cannot see — cutting the watchlist only removes diversification.

Conclusion: don't screen the watchlist by any per-symbol drawdown or ratio metric. If capacity is genuinely constrained (fill rate materially under ~50%, check Portfolio Sim first), trim by **expectancy percentile within timeframe** — the same ranking `edge_analysis.js` already uses — not by a DD cap. At the fill rates this watchlist actually runs (73-96% across 2H/4H at 10 slots), there's no capacity problem to solve by trimming at all.

### Slot contention: evicting the worst open position for a new signal isn't buildable honestly, and the reason it looks good is the reason it wouldn't work

Tested 2026-07-25. At 15 slots on 2H+4H `flip-only`, **33% of signals are turned away for lack of a slot, and 96% of those would, in hindsight, have out-earned the single worst-held position** (`contention.wouldBeatPct` in `portfolio_sim.js` — a pure retrospective comparison of two already-known final outcomes, needs no fill simulation, always computed regardless of `evictPolicy`).

Acting on that requires knowing a position is a loser before it closes, which the trade log cannot supply — it stores each position's final entry/exit price and MAE/MFE only, no bar-by-bar path. `evictPolicy: "oracle-worst-final"` exists as upper-bound tooling to test whether the idea is even worth pursuing: it decides using the open position's already-known FINAL `pnl_pct` (available immediately since a position in this simulator IS its closed trade-log row from the moment it "opens") and fills the early exit via straight-line interpolation of that final result over elapsed calendar time — a stand-in for a real intrabar mark, verified by hand against a real MEXX/TNA overlap (a −12.2% eventual loss, evicted 30% of the way through its natural hold, correctly priced at −3.7%).

**The result is dramatic and specifically not real**: CAGR 29.6% → 77.2%, max drawdown 9.6% → 2.2% at 15 slots (bigger at fewer slots: 5-slot CAGR/DD goes 2.55 → 111.96). The oracle wins by cutting long losing trades short **before they finish losing** — exactly the mechanism the real Stop Loss variant already tried and lost with (see the Stop Loss section above): longs recover a long way from their worst point on average (13.4% adverse excursion vs. −2.5% final), so a rule that can't tell "temporarily down" from "doomed" cuts far more recoverable trades than terminal ones. The oracle's edge is entirely foreknowledge that has no honest equivalent. **Do not read the oracle CAGR as an achievable number**, and do not build the bar-level OHLCV engine a real version would need — the Stop Loss result is already strong evidence a realistic version fails the same way.

One caught-and-fixed bug worth remembering if this is touched again: `taken[]` (the record win rate/profit factor/per-symbol P&L are built from) is created at ENTRY time carrying the position's full final result. An eviction must overwrite that record (`pos.takenRef`, added for exactly this) with the interpolated partial actually realized — the cash/equity side already had it right, but the secondary stats didn't until this was found by reconciling `perSymbol` P&L against `finalEquity` by hand.

### Watchlist selection mechanics (why stale symbol lists happen)

Scans resolve each watchlist's members by selecting it in the TradingView panel and reading the rows; if that fails they **silently fall back to the baseline's stored symbol list** — so a broken `watchlist.select()` freezes memberships at whatever was last captured, with no visible error (this shipped alerts for symbols removed from the list weeks earlier). The full sync cadence is twice daily (first scheduled scan after 9:15 AM ET, first at/after close, tracked in `status/watchlist-sync-state.json`) plus a live per-watchlist read on every scan and a full seed on every dashboard "Run Scan Now". Hard-won mechanics in `src/core/watchlist.js` if this breaks again:

- The list-picker dropdown opens via `[data-name="base-watchlist-widget-button"]` — the older `watchlists-button`/aria-label selectors click the wrong element in current TV builds.
- The dropdown only shows **recently-used** lists. Items there don't respond to synthetic MouseEvents; measure the item's rect page-side and deliver a **real CDP mouse click** at its coordinates.
- Every other list is only reachable via the **Shift+W "Open list…" dialog**, whose "Search lists" input is auto-focused on open. Its rows respond to **neither synthetic nor real coordinate clicks** — the only working automation is keyboard: CDP `insertText(name)` to filter → `ArrowDown` → `Enter`.
- Verify success by polling `getActiveName()` (the widget button's text) — never trust that a click/Enter "worked".

### Dashboard "Watchlist Symbols" panel going blank is a display bug, not a seeding failure — fixed 2026-07-28

Diagnosed after the panel showed "0 watchlist(s) / No watchlist data available yet" the same day the user had edited a watchlist's membership in TradingView, which looked exactly like the seeding failure the section above describes. It wasn't: `swing-signal-baseline.json`'s `watchlists` had fresh, correct symbol lists (`source: "data_attributes"`, a genuine live read) from that morning's sync. The bug was purely in what the dashboard displayed.

Root cause: the full live resync (`syncWatchlistSymbolsFromTradingView()`) only runs once or twice a day (gated by `status/watchlist-sync-state.json`'s open/close dates — see above), so `result.watchlist_sync` was `[]` on every OTHER scan that day. `writeLatestStatus()` overwrites the *entire* status file every run, so that empty array clobbered whatever the sync scan had written minutes earlier. The panel showed real data for roughly the 15-minute window between a sync scan and the next regular one, then went blank for the rest of the day — every single day, for as long as this code existed, which is why it read as "seeding failed today" despite the underlying data being fine.

Fixed by `buildWatchlistSyncFromBaseline()` in `morning.js`: when the current scan didn't run a live resync, `result.watchlist_sync` is now built from the persisted `baseline.watchlists` instead of left empty — same data the "why stale symbol lists happen" section already establishes as the real source of truth, just also used for display now instead of only for scanning. Two smaller bugs fixed alongside it, both harmless but worth knowing: the live-sync path never included `timeframe` in its `synced` array (the panel always showed "TF ?" even when data was fresh), and the dashboard's `sourceLabel` map only recognized 3 old values (`tradingview_panel`/`rules_fallback`/`watchlist_unavailable`) — `data_attributes` and `text_scan` (the two `watchlist.js` actually returns on a successful live read, see below) fell through to an unstyled raw-string badge instead of the green "Live from TradingView" one.

**If the panel goes blank again, check `swing-signal-baseline.json`'s `watchlists` field directly before assuming a seeding failure** — that file is the ground truth; the dashboard is just a view over it.

### Trade-log orphan detection — bundled with reconciliation, archiving stays manual (2026-07-28)

`scripts/archive_trade_log.js --orphans` (see the "Closed-trade log" section above) already existed to move a dropped symbol's history into `trade-log/archive/` so it stops skewing Edge Analysis/Portfolio Sim — but nothing ever reminded anyone to run it, so orphans (e.g. `DXYZ`, fully removed from every watchlist) sat in the active log unnoticed.

`findWatchlistOrphans(baseline)` in `trade_log.js` is the read-only detection half: diffs tickers present in the active (non-archived) trade log against `baseline.watchlists` membership, exchange-prefix-insensitive. `morning.js`'s `runSignalJob()` calls it right after a **real** watchlist reconciliation (`syncResult.synced.length > 0` — the twice-daily open/close sync, not every 15-min scan) and persists the result onto `baseline.trade_log_orphans` via a direct field patch (same `parseJsonFile`/`writeJsonFile` pair `syncWatchlistSymbolsFromTradingView` already uses), then surfaces it as `result.trade_log_orphans` → `createDashboardStatus()`'s `tradeLogOrphans` field. **Deliberately persisted, not left empty on non-sync runs** — the exact same reasoning as `buildWatchlistSyncFromBaseline` above: `writeLatestStatus()` overwrites the whole status file every run, so an in-memory-only value would flicker to empty between reconciliations.

**Detection is automatic; archiving is not.** The dashboard (Open Trades card) shows a banner listing orphaned tickers with trade counts/timeframes and an "Archive Now" button, confirm-gated, that POSTs to `/api/archive-orphans` — which shells out to the *exact same* `archive_trade_log.js --orphans` CLI script via `spawn` rather than reimplementing its row-moving logic, guarded by the server's `runExclusive` lock (a live scan appends to the same CSVs this rewrites in full; overlapping read-modify-write could drop an appended row). On success the endpoint recomputes and directly patches both `baseline.trade_log_orphans` and the status file's `tradeLogOrphans` so the banner clears immediately rather than waiting for the next reconciliation.

This was a deliberate choice over full auto-archiving on the reconciliation path itself, even though the action is reversible (`--restore`): it mirrors the precedent already set by the strategy-identity guard above ("suspend and flag, no auto-repair") — an automated job silently rewriting trade-history CSVs off a watchlist read that has a documented history of occasionally failing/falling back (see "Watchlist selection mechanics" above) is a worse failure mode than a banner that's one confirm-click away from doing the same thing correctly. User confirmed this tradeoff explicitly when it was proposed.

**Detection was gated on the sync event and therefore never ran at all — fixed 2026-07-29, plus a manual sweep.** The call above was wrapped in `if (syncResult?.synced.length > 0)`, i.e. only after a live twice-daily reconciliation. **This is the exact mistake `buildWatchlistSyncFromBaseline` was written to fix for the watchlist panel** (see that section above): the gate keys on the *sync event* while the data source is `baseline.watchlists`, which is the persisted source of truth and is equally valid on a scan that didn't resync. Consequence, found when the user reported removed symbols not appearing: `baseline.trade_log_orphans` was still `null` with **12 real orphans present and membership synced hours earlier** (`RETL` 101 trades, `AGQ` 76, `DXYZ` 73, …), so the card had been claiming "No orphaned symbols detected" for the entire life of the feature — no run had ever satisfied the gate. Now recomputed on **every** scan.

Two things that fix depends on:
- **`findWatchlistOrphans` returns `[]` when the allowlisted membership is empty.** Without the sync gate, a baseline with no usable watchlist data would otherwise report *every logged ticker* as an orphan and offer to archive the whole trade log. Empty membership means "unknown", not "everything is orphaned" — verified both the empty-baseline and no-allowlist-match cases return 0.
- **`POST /api/detect-orphans`** ("Sweep now" on the card) is read-only over the trade log + baseline, needs no TradingView and no scan, and finishes in under a second. It **does not** resync watchlist membership, so it returns `membershipAsOf`/`membershipOldest` (computed from configured watchlists only — dead renamed entries would misreport freshness) and the card states them, warning if over a day old. Recomputing can only ever be as fresh as the last reconciliation, and implying otherwise would be worse than not showing a timestamp at all.

### TradingView alert orphan cleanup — the `excursion_alerts` twin of the trade-log orphan check (2026-07-28)

Same root cause as the trade-log orphans above, different consequence: `createExcursionAlerts()` creates real TradingView price alerts (stop/target pairs) for open positions and records them in `baseline.excursion_alerts`; `processLevelViolationsAndCleanup()`'s EXIT-driven pass deletes them once a scan observes that position closing. But that pass only runs for entries actually present in a scan's `results` — a symbol/timeframe dropped from its watchlist before (or without) that ever happening leaves the alert with **no path back to cleanup at all**. It just sits active on TradingView until it self-fires or hits its ~30-day expiration.

Confirmed live before the fix (`baseline.pending_alert_cleanup` had never once been populated in this project's history): `TSLA|1D` and `USO|60`/`EDC|60` (dropped from their watchlists) carried 6 active, never-fired alerts with no way to ever clean them up, and `MU|30`'s stop-side alert had already self-fired hours earlier, completely unnoticed, because `MU|30` hadn't been scanned since dropping out of "Swing 30m".

`findOrphanedExcursionAlerts(baseline, watchlistNames)` in `morning.js` is the detection half — diffs `excursion_alerts` keys (`SYMBOL|rawTimeframe`) against current watchlist membership, exchange-prefix-insensitive, mirroring `findWatchlistOrphans`. Wired into `processLevelViolationsAndCleanup()`, which already runs unattended on every scan: orphans with a real `alert_ids` array get queued into the existing `pending_alert_cleanup` (the same mechanism the EXIT-driven pass uses) so `drainPendingAlertCleanup()` — already unconditional, no confirm-gate, since deleting a stale price alert touches no capital — deletes them for real on the same run. Local-only orphaned entries (no real alert, just bookkeeping) are deleted directly, nothing to queue.

**A bug in this very fix, caught before it shipped wrong:** `baseline.watchlists` accumulates dead entries under old names forever — nothing ever prunes them on a rename, since `syncWatchlistSymbolsFromTradingView()` only ever iterates `rules.json`'s *currently configured* names. Live example: `"Swing 30min"` (an old name) still sits in the baseline with real symbol data, superseded by `"Swing 30m"`. The first version of `findOrphanedExcursionAlerts` (and, it turns out, the pre-existing `findWatchlistOrphans` too) treated every `baseline.watchlists` key as equally valid — which meant `MU|30` (only ever present under the dead `"Swing 30min"` entry) read as "still in a watchlist" and would have been the one case this fix was built to catch that it *missed*. Both functions now take a `watchlistNames` allowlist (`Object.keys(rules.watchlists)`, threaded through from every call site) and ignore any `baseline.watchlists` entry whose name isn't in it. Verified the fix against real data before and after: pre-fix, `MU|30` was invisible to the orphan check; post-fix, it was correctly caught alongside `TSLA`/`USO`/`EDC`.

All four were drained for real 2026-07-28 (`alerts.deleteAlerts`), confirmed via a live `alert_list` before/after (47 → 39 active-eligible alerts, exactly the 8 alert_ids across the 4 positions). If this needs re-checking: `swing-signal-baseline.json`'s `pending_alert_cleanup` should be empty/absent in steady state — a nonzero, non-shrinking count across multiple scans means `drainPendingAlertCleanup` is failing (check for a `alerts.deleteAlerts` error in the console), not that nothing is orphaned.

### Webhook dedupe key format mismatch — manual Send and auto-dispatch silently used different keys (found + fixed 2026-07-28)

While building the webhook-priority feature below, checking "is this open position webhook-sent" surfaced a real, pre-existing bug: the manual Send button's dedupe key and the auto-dispatch path's dedupe key were built from **differently formatted** entry times for the exact same position, so they never matched each other.

- Manual Send (`dashboard/index.html`'s `webhookSentKey()`) sourced `entryTime` from `status.openTrades` rows — which `buildOpenTrades()` runs through `formatEntryTimeDisplay()` for human display, e.g. `"07/20/2026, 10:30:00 AM ET"`.
- Auto-dispatch (`dispatchTradeWebhooks`/`dispatchExitWebhooks`, fed by `notify_signal_events`) reads `entry.trade.entryTime` straight off the scan result — the raw ISO string from `data.js`, e.g. `"2026-07-20T14:30:00.000Z"`.

`sentKey()` builds `ticker|tag|entryTime` verbatim from whatever string it's given, so the *same logical position* produced two different keys depending on which path sent it. Confirmed live: `TSX_DLY:TD`'s manually-sent 30m position was recorded under the display-formatted key; the auto-exit dispatcher (which only ever computes the raw-ISO form) would never have found it, meaning **the exit side of the feature immediately below would have silently never fired for any manually-sent position** — exactly the case the user's own example (`TD`) is.

Fixed by threading a second, canonical field — `entryTimeRaw` — through every place an open-trade row is built (`buildOpenTrades()`'s three passes, all four row constructions in `buildPriorSignalsByWatchlist()`), carrying the untouched raw ISO value alongside the display-formatted `entryTime`. The dashboard's `webhookSentKey()`/`buildWebhookCell()` and `createExcursionAlerts()`'s webhook-sent check now key on `entryTimeRaw`, matching the auto-dispatch path exactly. The one pre-existing ledger entry recorded under the old display-formatted key (`TD`'s) was migrated by hand to the raw-ISO key so it isn't silently duplicated on a future manual re-send.

**If a webhook-sent check ever looks wrong again**, check whether the row it's reading came from `buildOpenTrades()`/`priorSignalsByWatchlist` (has `entryTimeRaw`) or was constructed some other way (might not) — a `null` `entryTimeRaw` is a real "no reliable key" case, not a bug to route around by falling back to the display string.

### Webhook-sent positions get alert-quota priority, with eviction (2026-07-28)

The account's TradingView alert quota (`MAX_ALERTS = 20` active alerts, in `createExcursionAlerts()`) is shared across every open position, allocated first-come in whatever order `openTrades` happens to iterate — with no relationship to which positions actually have real money on them via the trade-webhook. Confirmed live: `TSX_DLY:TD` had a webhook sent (a real order placed) but only local (scan-interval) monitoring, `"Local alert 15/64"`, because unrelated positions without any webhook activity had already consumed the quota by the time TD's turn came up in the loop.

Fixed with two additions to `createExcursionAlerts()`:
- **`webhookSentKeys`**: built once per call from `openTrades`, using each trade's `entryTimeRaw` (see the key-format fix above — this is precisely why that fix had to land first) through `sentKey()`/`alreadySent()`. `openTrades` is then stable-sorted webhook-sent-first, so those positions are attempted before quota fills up with lower-priority ones.
- **Eviction**: if a webhook-sent trade still hits the quota wall, `findEvictionCandidate()` picks the best non-webhook-sent `created:true` entry from `baseline.excursion_alerts` to sacrifice — **longest timeframe first** (via the existing `timeframeToMinutes()`), since a 1D/4H position loses the least by dropping to local-only monitoring (it was only ever going to be checked once per its own long scan interval anyway; a 15m position would lose far more precision for the same downgrade). The evicted entry's real alert is deleted (`alerts.deleteAlerts`), its baseline entry downgraded to `created:false` with an explanatory `skip_reason`, and `usedSlots` is **re-checked via a fresh `alerts.list()`** rather than assumed — one side of a stop/target pair can already be self-fired-and-inactive, so subtracting the full pair's length would overcount how many active slots the eviction actually freed. Never evicts another webhook-sent position (checked both raw and normalized-ticker key forms).

Verified 2026-07-28: `webhookSentKeys` correctly resolves `TD`'s entry (`alreadySent` → true post-fix), and `findEvictionCandidate`'s longest-timeframe selection picked `BSE_DLY:SBIN|240` (4H) as the top candidate over the remaining shorter-timeframe holders — both checked against real baseline data. Not yet witnessed live mid-eviction: the same-day orphan cleanup above freed enough quota (14/20 active afterward) that TD's next real alert creation won't need to evict anything to succeed.

Also marks the alert message itself: a webhook-sent position's stop/target alerts get `| Open Pos` inserted (e.g. `TD 30m | Open Pos | Stop avg MAE 8.79% | Entry 933.13`), computed from the same `isWebhookSent` check, so a real order is identifiable straight from the TradingView alert list/push notification without cross-referencing the dashboard. Confirmed nothing in this codebase parses alert `message` text back for logic (unlike Pine chart labels, which the signal-detection path does read) — purely a human-facing marker, safe to change format on freely.

**Historical view**: Symbol Lookup's Closed Trades table also shows a `webhook` column per row (`webhookStatusForRow()` in `symbol_lookup.js`), reusing the exact same `sentKey()` computation — trade-log rows already carry `ticker`/`timeframe` in the bare/label form `sentKey()`/`timeframeTag()`/`bareTicker()` are idempotent over, so only `entry_time_ms → ISO` needs converting. Verified the key this produces for a hypothetical closed TD 30m row matches the real, already-migrated ledger key exactly. Shows `✓ entry only` vs `✓ entry+exit` vs `—` (never sent) — a read of what the ledger recorded for that entry, not a live status.

### Price-alert auto-creation and local-monitoring pushes are now scoped to webhook-sent positions only (2026-07-29)

As the watchlist universe grew significantly (more symbols across more timeframes), the alert-quota-priority mechanism above stopped being enough — even a webhook-sent position's neighbors (positions with no real order placed anywhere) were still auto-creating real TradingView alerts and, once those hit the quota wall, falling back to local (scan-interval) monitoring that pushed a `LEVEL HIT` line to ntfy for every stop/target crossing regardless of whether any money was actually on that position. User request: only webhook-sent positions should get automatic price alerts (real TV alert or local-monitor fallback); everything else is the user's own manual call, "as needed."

Two call sites needed the same gate, checked fresh per position rather than trusted from a stored flag (webhook-sent status can change after a position's `excursion_alerts` entry was first written):

- **`createExcursionAlerts()`**: right after computing `isWebhookSent` (already existed for the eviction-priority logic above), a new branch short-circuits for `!isWebhookSent` — stats/levels are still computed and persisted (the dashboard's Alert Levels column still shows suggested stop/target for the user to act on manually), but `alerts.create()` is never called and the trade never enters the quota/eviction logic at all. The stored `skip_reason` becomes `"No webhook sent — auto-alert creation disabled, create manually if needed"`, distinct from the genuine-quota-overflow `"Local alert i/n"` label (which now only ever applies to a webhook-sent trade that still couldn't get a slot even after eviction — a much rarer case). Pre-existing real alerts on non-webhook positions (created before this policy shipped) are **left untouched** — the "already created" early-return at the top of the loop already skips reprocessing them, matching the standing preference for confirm-gated/manual over silently tearing down something a scan didn't just create.
- **`processLevelViolationsAndCleanup()`**: the entire per-entry level-check block (the `stopMax`/`targetMax`/`stopAvg`/`targetAvg` `checks` loop that produces `violations`/`violation_lines`) is now gated on a fresh `sentKey(...)` + `alreadySent(...)` check built from `entry.trade.entryTime` (the raw ISO, same field the dedupe-key fix above established as canonical) — not on `stored.created`, since a `created:true` entry could be a legacy non-webhook alert that should no longer generate local-monitor noise either. EXIT-driven cleanup and orphan cleanup (both unrelated to monitoring/noise) are untouched.

Net effect on the two separate ntfy pushes in `runSignalJob()` (`notify_signal_lines` under the title "TradingView signal scan", `levelCheck.violation_lines` under "TradingView level alert"): the first (real trade OPEN/EXIT signals) is unaffected; the second now only ever fires for webhook-sent positions, which is what "only signal alerts to ntfy, price alerts only if webhook is sent" (the user's framing) actually meant in code terms — there was never a single unified "noise" switch, just two independent paths that both needed the same webhook-sent gate.

### Manual webhook Send gained a market/limit order-type picker (2026-07-29)

The original ask was for the *scanner* to auto-compute a limit price from bid/ask (midpoint + $0.02 buffer, skip `order_type` entirely if the spread is under $0.02) and send it automatically. Checked live before building it: `quote_get` on the current chart symbol returned no `bid`/`ask` at all — those fields in `getQuote()` (`data.js`) come from a best-effort DOM scrape of a bid/ask panel that isn't part of the standard chart layout this scanner uses, so an automatic version would have silently fallen back to a plain market order almost every time, exactly the kind of "always hits the fallback branch" trap this project's history keeps finding. User redirected instead to a manual control: an order-type dropdown + price input on the dashboard's per-row manual Send button, entry side only (auto-exit dispatch and the fully-automatic scheduled entry dispatch both still always send a plain market order — there's no human present in either path to pick a type or type in a price).

- `buildWebhookPayload()` (`trade_webhook.js`) takes an `orderType` param; `orderType === "limit"` adds `order_type: "limit"` to the payload, anything else omits the field entirely (unchanged shape from before this feature).
- Dashboard: `buildWebhookCell()` renders a `<select>` (Market/Limit) + a price `<input>` (hidden unless Limit is selected) instead of a static pre-baked payload; `wireWebhookButtons()` reads both live at click time. Market keeps sending the row's existing `entryPrice` exactly as before; Limit requires a positive numeric price client-side before allowing Send.
- `/api/send-webhook` (`serve_signal_status.js`) re-validates the limit price server-side (`orderType === 'limit'` requires a finite positive `price`) rather than trusting the client — this sends a real order, so the check can't live in the browser alone.
- The automatic paths (`dispatchTradeWebhooks`/`dispatchExitWebhooks` in `morning.js`) were deliberately left unchanged — no `orderType` is ever passed there, so they keep omitting `order_type` exactly as before this feature shipped.

**Superseded the same day by the full order-type matrix below — and that section documents a real bug in the version above: it sent only `price` and never `limit_price`, which the executor rejects with HTTP 400.**

### Full `order_type` / `time_in_force` support, and a manual Close button (2026-07-29)

The user supplied the Railway executor's own contract: neither field is validated there, both are lowercased and passed straight to Alpaca as `type`/`time_in_force`, so a bad *value* fails at the broker — but a priced order type **missing its required price is rejected up front with HTTP 400 and never reaches Alpaca**. `order_type` ∈ market (default) / limit (needs `limit_price`) / stop (`stop_price`) / stop_limit (both) / trailing_stop (`trail_percent` **or** `trail_price`; TIF force-set to `gtc`, `quantity` ignored, only survives as a trailing stop on `letf`-routed sells). `time_in_force` ∈ gtc (default) / day / opg (at-open; unfilled OPG orders are resubmitted as market at 9:35 AM ET) / cls / ioc / fok — and `opg`/`cls` are valid only on market or limit.

`validateOrderSpec()` in `trade_webhook.js` is the single definition of "valid", used by the dashboard form **and re-run server-side on every send** (`/api/send-webhook`, `/api/send-webhook-exit`). Three decisions inside it worth keeping:
- **`0` counts as missing, not as a price.** An order at 0 is a real, very wrong order.
- **`opg`/`cls` on a non-market/limit type is refused, not silently reinterpreted**, and likewise for a TIF on a trailing stop (which the executor force-sets to `gtc` anyway) — reinterpreting would leave the UI claiming something the broker never did.
- **`trail_percent` wins when both trail fields are given**, since it's the one that survives the `letf`-routed sell path and sending both leaves the choice to field ordering.

`buildWebhookPayload()` throws on an invalid spec rather than emitting a partial payload, and **a `market` order still produces the original payload byte-for-byte** (`{symbol, side, group, tag, price, secret}` — no `order_type` key), so the existing armed auto-send path is provably unchanged. `price` keeps its TradingView meaning of "the order's price" and therefore carries `limitPrice ?? stopPrice ?? reference` for a priced type, while the field the executor actually reads (`limit_price`/`stop_price`) is always sent separately. `/api/webhook-config` serves `ORDER_TYPES`/`TIME_IN_FORCE` so the dropdowns can never offer a value the validator would reject.

**New: a manual Close button** (`/api/send-webhook-exit`) on any open position whose *entry* is in the webhook ledger — the hand-operated twin of `dispatchExitWebhooks`, added as the slot-freeing action for the Edge-ranking work below. Scoped identically to the automatic exit path and for the same reason (closing a position the executor was never told about could error out or open an unintended opposite position): it refuses unless `readSentState().sent[key]` exists, refuses a second time if `.exit` is already recorded, and derives the closing action by inverting the **recorded** entry side (`entryRecord.side`) rather than re-deriving it from the position's LONG/SHORT — the ledger is the only record of what actually went out, and it cannot disagree with itself.

Open-trade rows also gained a real `side` field (`entry.trade?.side`, threaded through all three row constructions in `buildOpenTrades` plus the trade-backed row in `buildPriorSignalsByWatchlist`). It was simply absent before, so `buildWebhookCell`'s `row.side || 'LONG'` fallback meant **every manual send went out as a buy**, including on a short.

Verified live 2026-07-29 with nothing sent — every invalid case was refused before the fetch: limit without a price, limit price `0`, stop without a price, stop_limit with only the limit leg, trailing without either trail field, `opg` on a stop, `cls` on a trailing stop, unknown type, unknown TIF, close on a position with no ledger entry, close without an entry time. All 8 valid payload shapes were inspected by hand.

### Ranking open positions for a fixed-slot portfolio: the Edge column and the Org/New pair (2026-07-29)

The user runs a **max-15-position book** and asked for a measure, shown as a column, to avoid buying a weak position — attaching a TradingView Key Stats screenshot (Sharpe ratio, expected payoff, average PnL, winners %, average profit / average loss, largest profit / largest loss) as candidate KPIs.

**Of those KPIs only "Expected payoff" (= expectancy) is used in the score**, and that is measured, not preferred: the walk-forward numbers in the "Ranking symbols" section above put expectancy at +0.381 while profitFactor (−0.168), sharpe (−0.133), cagrDd (−0.145) and winRate (−0.018) all rank at or *below* random out-of-sample. The rest of the panel's numbers are shown in the Edge cell's tooltip as diagnostics only (`edgeTooltip()` — expectancy, win rate, avg-win/avg-loss ratio, profit factor, avg hold, trade count, rule variant). If asked to "add Sharpe to the ranking", the answer is that it was tested here and it ranks worse than nothing.

`buildSymbolEdgeScores({ruleType})` in `edge_analysis.js` computes, per `TICKER|tflabel`, the **expectancy percentile within that timeframe × 100**. Percentile rather than the raw value for two reasons, both already established above: expectancy scales hard with timeframe (15m ~1.7%/trade vs 4H ~7%) so a raw ranking is really a timeframe ranking, and the percentile is what makes rows comparable **across** timeframes for a whole-book slot cap. Same 8-closed-trade floor (`RANK_MIN_TRADES`) and 4-ranked-peer floor as `buildEdgeAnalysis` — below either, `score` is `null`.

`attachOpenTradeRanks(openTrades, {ruleType, isNew})` joins those scores onto the open-trade rows and assigns the two ranks the user asked for, both within the row's own timeframe:
- `edgeRankOrg` — rank among positions **already open before this scan's new arrivals**; `null` on a new arrival, which the dashboard renders as "new".
- `edgeRankNew` — rank among **every** position now open on that timeframe, with a drift arrow when the two disagree.

One rank alone cannot show displacement: the ranks only move because the *set* changed, which is exactly the event the request is about. Verified live on Swing 45m — LFST held 1/10 → 1/14, TEX arrived today at new → 3/14 and pushed OII from 3/10 → 4/14; 23 of 135 open positions were same-day entries.

Wiring details that are easy to get wrong:
- Called in `runBrief()` **after** `createExcursionAlerts`/`enrichOpenTradesFromBaseline`, inside a try/catch. The fields are purely additive and nothing downstream gates on them, so a failure must cost a log line, never the scan's open-trades data.
- `isNew` is passed in as a predicate rather than computed in `edge_analysis.js`, keeping the ET trading-day calendar in `morning.js` which owns it. It is the same same-ET-day test the notify/webhook gates use.
- `ruleType` defaults to the most-traded variant (`tradeLog.listRuleTypes()[0]`), never a pool of all variants — same rule every other trade-log consumer follows, since pooling would average two exit regimes into one meaningless expectancy.
- A `null` rank on a row that is **not** a new entry means ranking never ran for that snapshot (a pre-feature status file, or the try/catch fired). `buildRankCells` renders that as "—", not "new" — the two must not be conflated.

**The portfolio cap** is a `maxPositions` number input on the Open Trades card (default 15, `localStorage`, client-side only — it changes nothing about scanning or ordering, so it should not need a scan or a restart to adjust). `applyPortfolioCap()` pools every open position across all timeframes by Edge score, flags rows ranked below the cap as over-cap, and surfaces the weakest three in the card header. **Unscored rows are never flagged over-cap**: "not enough history to judge" must not read as "weak", or the cap would recommend liquidating positions purely for being new to the trade log.

**The answer to "what's the best method to select a good signal":** use Edge as a **filter, not a priority order**. Per the "Ranking is a filter, not a priority" section above, reordering which signal to take when several fire barely moved anything (simultaneous signals are rare), while dropping the bottom half by past expectancy moved a lot — but only when capacity-constrained (5 of 5 split points helped at 5 slots; only 3 of 5, twice materially negative, at 10). A 15-slot cap against the ~135 positions currently open is roughly 11% of the book, which is deep inside the regime where selection pays. And do **not** add a drawdown or ratio screen on top — tested and rejected 2026-07-25; it inverts on expectancy and loses on both CAGR and portfolio drawdown.

### TradingView-alert timeframes now record into the webhook ledger (2026-07-29)

The subscription's two watchlist alerts POST to the Railway executor **directly**, so for those timeframes a real order exists that this system never sent and therefore had no record of. Once price-alert creation and level monitoring were scoped to webhook-sent positions (section above), that hole became load-bearing: a live-money position placed by a TradingView alert got *no* monitoring, lost the alert quota to positions with no money on them, still showed a "Send" button (duplicate-order risk), and had no single place to reconcile against the executor's own portfolio.

`webhook.tv_alert_timeframes` in `rules.json` (non-sensitive, same as `enabled_timeframes`) marks a timeframe as "TradingView places the order". `recordTvAlertLedger()` in `morning.js` then writes the **same ledger record the scanner would have written** — `recordSent`/`recordExitSent` with `sent: false, source: "tv-alert"` — and sends nothing. Every consumer already keys on `alreadySent(key)` existence, so alert creation, level monitoring, quota priority and the duplicate-send guard all start working for those positions with no further changes.

Four decisions in this that are easy to undo by accident:
- **The two lists are mutually exclusive, enforced in two places.** `loadWebhookSettings()` filters any tv-alert timeframe out of `enabledTimeframes`, and `/api/webhook-toggle` (now taking `mode: 'auto' | 'tv-alert'`) removes from the other list when setting one. A timeframe in both would mean two real orders for one signal, so the conflict resolves in favour of tv-alert rather than being reported and left.
- **Deliberately NOT gated on `notify`**, unlike `dispatchTradeWebhooks`/`dispatchExitWebhooks`. This sends nothing — it writes down an order somebody else already placed. Gating it would leave holes in the ledger on any day a manual scan first observed the position, and completeness is the entire point of the mode.
- **An EXIT whose entry isn't in the ledger is skipped, not invented** (`entry_not_in_ledger`). Recording an entry retroactively would claim an entry order existed for a position that predates the toggle. Null entry time is skipped too, same reasoning as everywhere else.
- **Auto-exit can't double-fire** because `dispatchExitWebhooks` gates on `enabledTimeframes`, which mutual exclusivity guarantees never contains a tv-alert timeframe. Nothing extra was needed for this, but it's the invariant to preserve if the exclusivity is ever relaxed.

The dashboard labels these rows `◆ via TV alert` / `◆ closed by TV alert` rather than `✓ sent`, so "we placed this" and "we observed this" stay distinguishable when reconciling. Verified 2026-07-29 against the real module with a throwaway ticker (ledger backed up and restored afterward): entry recorded with `sent:false`, re-run idempotent, exit merged onto the same key, a non-listed timeframe ignored, an exit with no entry refused, a null entry time skipped.

A manual-ledger retry path was added for failed or partial TV alert creations. Rows whose `TV alert` status is `failed` or `partial` can now retry alert creation through `POST /api/manual-ledger/:id/retry-alerts`, reusing the existing ledger entry rather than recreating it.

### Executor portfolio (`src/core/executor_portfolio.js`) — the only real source of truth (2026-07-29)

User's framing: the Railway app has portfolio info, "which would be a good source of truth to closely monitor the portfolio position sizing." That's exactly right and worth stating plainly — **everything else in this project is inference.** The scanner reads TradingView's strategy output and records what it *sent*; the trade log records what the strategy *backtested*. Neither knows what the broker actually holds or at what size. `/api/executor-portfolio` fetches the executor's own positions and reports the **difference** against the ledger, without deciding which side is right.

**Built shape-agnostic because the response schema was unknown** (the Railway MCP was unauthorized — `railway login` needed — so the route couldn't be discovered, and the user chose "build it configurable, shape-agnostic" over supplying a sample). `pickArray()` finds the positions list at the top level, under a named wrapper (`positions`/`holdings`/`portfolio`/`openPositions`/`data`/`items`/`results`/`assets`), as any top-level array of objects, or one level of nesting — deliberately **not** arbitrarily deep, so a stray array elsewhere in a bigger payload can't be mistaken for the position list. `pickField()` matches candidate key names after normalizing case/underscores/dashes (`avgEntryPrice` ≡ `avg_entry_price` ≡ `AVG-ENTRY-PRICE`). **An unmapped field yields null and is never inferred from a neighbouring field** — a wrong quantity or price would read as a real reconciliation break. Verified against 6 plausible shapes including nested wrappers, camelCase, exchange-prefixed symbols and negative-qty shorts.

Two normalization judgements that could bite:
- **Side falls back to the sign of quantity** when no explicit side field exists (negative = short). That's a near-universal encoding, and it's reading one field's own sign rather than guessing from a different field.
- **`unrealizedPct` under ±1 in magnitude is treated as a fraction** and scaled ×100 (`0.0084` → `0.84%`). The alternative reading — a genuine ±0.03% move — is far less likely, and the UI labels it as percent either way so a wrong scale shows up rather than hiding.

`rawSample` (the first returned row) is always included in the response and rendered in a collapsible block. That is the intended path for tightening the field mapping later — no code change needed to inspect the real schema.

**Reconciliation keys by bare ticker with the ledger side aggregated.** This is the one real subtlety: the ledger is per `ticker|timeframe` (one record per signal) while the broker holds **one position per ticker** regardless of how many timeframes signalled it. Matching per timeframe would report a spurious break for every multi-timeframe symbol. Three deliberately non-judgemental buckets: `matched`, `executorOnly` (broker holds it, no open ledger record — entered outside this system, or a close was recorded here that never filled), `ledgerOnly` (open ledger record, no broker position — entry never filled, or it closed at the broker before any scan saw the EXIT).

Sizing is reported as **weight (share of total portfolio value) against an even-split baseline of 100/N**, not as absolute size: absolute sizing needs account equity, which the endpoint may not return, and relative weight is what actually answers "is one position oversized". Auth defaults to `?secret=…` reusing the webhook secret (the GET analogue of the webhook's body field), overridable to `bearer`/`header`/`body`/`none` — and a 401/403 is surfaced **with its status and body snippet** in the card, because the whole point of a configurable auth mode is that getting it wrong has to be diagnosable without reading a server log.

The credential never reaches the browser (fetched server-side, same rule as the webhook secret), and open trades for the reconciliation come from the status file rather than a fresh scan — the endpoint has to answer in a second or two, and all it needs is "which tickers does the scanner think are open", which the last scan already established.

### `/api/restart` must never use `stdio: 'inherit'` (bug found + fixed 2026-07-29)

The restart endpoint spawned the replacement server with `stdio: 'inherit'`, so it wrote to whatever pipe the *original* process was launched with — and after the parent calls `process.exit(0)` nothing drains that pipe. The buffer fills after a handful of `console.log` calls and the next write **blocks the event loop indefinitely**.

The symptom is genuinely misleading and cost a debugging cycle here: the server answers `GET /api/webhook-config` fine while every POST that logs hangs with no error, no crash, and one healthy-looking process in the process list. Two successful `POST /api/webhook-toggle` calls (each one `console.log`) were enough to wedge it, after which even the non-logging 400 paths stopped responding.

Now spawns with `stdio: ['ignore', fd, fd]` against an appended `dashboard-server.log`, falling back to `'ignore'` if the file can't be opened (never refusing to restart over a log file). **If a dashboard server ever appears half-alive again, check `dashboard-server.log` and the spawn options first** — and don't diagnose it by process count, which looks correct throughout.

**The Edge score deliberately ignores the position's live P&L.** Cutting positions that are currently down has been tested twice here and lost both times (the Stop Loss variant, and the `oracle-worst-final` eviction upper bound) because longs recover a long way from their worst point on average — 13.4% adverse excursion against −2.5% final. Edge answers "is this symbol's average trade good on this timeframe", which is a question the trade log can actually answer.

### Push notifications (ntfy) — gating and failure visibility

- Notifications only fire when `runSignalJob` runs with `notify: true`. Only the real scheduled path sets that (`run_signal_job.ps1` → `run_signal_job.js --notify`) — every manual/dashboard-triggered scan (`/api/run-cron-now`, direct `runBrief` calls) explicitly passes `notify: false`, so ad-hoc testing/debugging can never leak a push.
- Eligibility (`notify_signal_lines` in `src/core/morning.js`) requires `entry.trade?.signal === 'OPEN'` — the confirmed Strategy Tester trade-table read, not the unreliable `Position: Long/Short` label — plus `isRecentTradeSignal`/`isSameTradingDay` (same ET calendar day, entry within ~4 bars). This makes the notify path stricter than the raw Open Trades table, which is why the false-positive open-trade bug above never produced a spurious push.
- The POST to `rules.ntfy.url` logs on failure (non-2xx response or fetch error) instead of swallowing it — check the console output / `signal-scan.log`. `run_signal_job.ps1` captures the job's stderr into `signal-scan.log` via a temp-file redirect (`2>$stderrFile`), not `2>&1` — this script has `$ErrorActionPreference = 'Stop'`, and `2>&1` on a native exe in PS 5.1 can turn a stderr line into a terminating error that aborts the whole script.
- To validate the wiring live without waiting for a real signal: POST directly to `rules.ntfy.url` with `Content-Type: text/plain` and `Title`/`Priority` headers (same shape as the real call) and confirm HTTP 200.

### Trade-execution webhook (`src/core/trade_webhook.js`) — the workaround for the 2-alert limit

The TradingView subscription only carries **two** watchlist alerts, and those already POST to the Railway executor directly. Every other timeframe would be ntfy-to-phone plus hand execution, which does not scale at 30m/45m cadence. This module lets the scanner emit the **same payload TradingView would have sent**, so the Railway side cannot tell the difference:

```json
{"symbol":"SOXL","side":"buy","group":"swing","tag":"15m","price":"42.105","secret":"..."}
```

Field semantics are copied from the alert template's placeholders, and getting any of them wrong produces a *valid-looking* order for the wrong thing: `symbol` is the **bare ticker** (`{{ticker}}` drops the exchange, so `BATS:SOXL` → `SOXL`), `side` is **lowercase buy/sell** (`{{strategy.order.action}}`) derived from the trade's own LONG/SHORT — never from `rules.chart.trade_direction`, which is a chart input that can change without this module knowing — and `price` is a **string**, because placeholder expansion produces strings and the receiver already parses that shape.

**Credentials never go in `rules.json` — that file is tracked in git.** URL and secret come from `TRADE_WEBHOOK_URL`/`TRADE_WEBHOOK_SECRET` or from `webhook.local.json` (gitignored); env wins. Only the non-sensitive switches (`webhook.group`, `webhook.enabled_timeframes`) live in rules.json, because the dashboard has to persist those. A missing secret is a hard refusal to send, never a send-without-auth. `/api/webhook-config` returns `hasSecret: true/false` and never the value.

**To configure:** edit `webhook.local.json` at the project root (create it if missing — it's gitignored, safe for secrets): `{"url": "https://your-railway-app.up.railway.app/webhook-path", "secret": "..."}`. Both fields are required — `configured` in `/api/webhook-config` is `Boolean(url && secret)`, so a filled secret with a blank `url` (or vice versa) still reads as unconfigured and every send is refused. Restart the dashboard server after editing (it holds config in memory, same as any other code/config change — see the hot-reload note above). Then arm the timeframes that should auto-send from the Open Trades card's per-watchlist-group header toggle (each one is a separate confirm dialog; arming is real-money-affecting once a scheduled scan with `--notify` runs). A manual per-row "Send" button also exists on any open trade regardless of arming, gated only by config + the dedupe ledger, with its own confirm dialog — useful for testing the wiring against one real position before arming a whole timeframe.

Three independent gates must all pass before an automatic order goes out, and each covers a different failure:
1. **`notify` is true** — only the real scheduled path (`run_signal_job.js --notify`) sets it, exactly as with ntfy, so no dashboard-triggered or ad-hoc debugging scan can ever place a live order.
2. **The timeframe is armed** in `webhook.enabled_timeframes` (per-timeframe opt-in, default empty, toggled from the Open Trades group header with a confirm dialog).
3. **`ticker|tag|entryTime` is not already in the ledger** (`status/webhook-sent-state.json`). This one is load-bearing: the same OPEN position is re-detected on *every* scan for as long as it stays open, so without it a 15-minute cadence would re-order the same entry all day. Entry time is in the key because it is precisely what changes when a genuinely new position opens on a symbol that already fired — keying on symbol+timeframe alone would suppress the next real entry forever. A **null entry time yields no key and is skipped**, never substituted (same reasoning as the open-trade `scanned_at` bug documented above).

Eligibility reuses the existing notify gating verbatim via `notify_signal_events` — a structured twin of `notify_signal_lines`, added because those lines are formatted for a phone lock screen and cannot be parsed back into fields. Same entries, same gates, never a looser set. Failed sends are deliberately **not** recorded as sent, so the next scan retries.

### Auto-exit dispatch — closes only positions this system itself opened via webhook (2026-07-28)

An entry sent via webhook (manual Send button *or* the auto-armed scheduled path — both write the same ledger record) does **not**, by itself, imply anything will fire when that position later closes. `dispatchTradeWebhooks()` only ever sends entry-side orders; there is no separate mechanism watching for the close. `dispatchExitWebhooks()` (`morning.js`, next to `dispatchTradeWebhooks`) adds that, deliberately scoped to **only close what this system knows it opened at the executor** — user-confirmed choice over the alternative (auto-exit on any EXIT signal on an armed timeframe, regardless of how the position was entered), because sending a close order for a position Railway was never told about could error out or, worse, open an unintended opposite position if the receiver doesn't validate.

- **Reuses the entry ledger as the "did we open this" signal**, rather than adding new state: `alreadySent(key)` (same `ticker|tag|entryTime` key an entry webhook was recorded under) must be true before an exit is even considered. `recordExitSent(key, ...)` in `trade_webhook.js` merges an `.exit` sub-object onto that *same* ledger entry (not a new key) — `alreadySent(key)` keeps meaning exactly "we sent the entry," `alreadyExitSent(key)` answers the paired question, and the two can never desync into separate records for one position.
- **A closed trade's `entryTime` is days-old by the time it exits** (it's when the position originally opened) — so recency has to be judged from a real exit timestamp instead. Added `exitTime`/`exitPrice` to the EXIT branch of `getStrategyPositionState()` in `data.js`, sourced from `reportData()`'s `lastClosedTrade.x.tm`/`x.p` (the same field `trade_log.js` already reads for `exit_time_ms`). The DOM-scrape fallback never populates these — a DOM-sourced EXIT is simply never treated as recent, not guessed at. This is also what fixed the "Signals Found" badge/list mismatch documented above; the two features share the same underlying field.
- **Side is inverted, not reused.** Closing a LONG is a *sell*; closing a SHORT is a *buy* (cover) — the opposite of what `orderAction()` computes for an entry with the same position side. `exitOrderAction()` in `trade_webhook.js` does the inversion; `buildWebhookPayload()` gained an `action` override parameter so the exit path can hand it a pre-resolved action without that action being re-run through the entry-side mapping a second time (which would have silently doubled the position instead of closing it).
- **Gates**: `notify:true`, an entry for this exact key is in the ledger (we opened it), that entry wasn't placed by a TradingView alert, `!alreadyExitSent(key)`. Failed sends are not recorded, same retry-on-next-scan behavior as the entry path.

**"Timeframe armed" was a gate here and had to be removed (2026-07-31).** Requiring `webhook.enabled_timeframes` to contain the timeframe meant a position entered with the **manual Send button** — explicitly supported on any timeframe, armed or not, and documented above as the way to test the wiring on one real position — could never be closed automatically. Found live: an `AME|1h` entry sent manually on 07-29 flipped short at 10:00 ET on 07-31 and no close order went out, because nothing was armed and `dispatchExitWebhooks` returned at its first line (`if (settings.enabledTimeframes.length === 0) return out`). The user closed it by hand.

The reasoning for the change, worth preserving because it looks like a loosening of a safety gate and isn't: **arming controls whether new capital is committed without a human; closing only ever unwinds a position a human already committed to.** Leaving a real position open at the broker *because a toggle isn't set* is strictly worse than the risk arming exists to control. The ledger record is the authorization — it is proof this system placed the entry.

Two things this change depends on:
- **tv-alert entries are excluded by the RECORD's `source`, not by the current config.** `getSentRecord(key).source === "tv-alert"` — checking `tvAlertTimeframes` instead would send a duplicate close for a position opened under that mode if the timeframe were later un-marked. TradingView sends its own close for those.
- **Consequence to state out loud when this ships:** every manually-sent position already in the ledger now gets an automatic close when it flips. Verified against the real ledger at the time (no network calls, gate logic only): `TD|30m`, `FTV|1h`, `FR|1h`, `OII|30m` → would send a close on their next EXIT; `AME|1h` and `UDOW|30m` → correctly `already_sent` (closed manually that day).

Key-matching was verified rather than assumed, because a mismatch here fails silently: the ledger key's entry time (captured from the open-trade read at send time) must equal the EXIT event's `entry.trade.entryTime` (from `reportData()`'s `lastClosedTrade.e.tm`). Checked on the real `UDOW|30m` — ledger `2026-07-29T14:00:00.000Z` against the closed row's `entry_time_ms` `2026-07-29T14:00:00.000Z`. Same value, so the close would have fired. This is the same class of bug as the display-vs-raw entry-time mismatch documented above; re-check it if auto-close ever appears to no-op.

### Webhook Orders tab — the ledger as its own view (2026-07-31)

`/api/webhook-ledger` + a `pane-webhook` tab: open (sent, no close recorded) with a per-row close, and full history filterable by symbol / timeframe / status.

**Reads the ledger directly rather than deriving from `openTrades`.** A webhook order can outlive the strategy position that prompted it — that mismatch is precisely what this tab exists to expose (see `findUnclosedWebhookExits` below), so deriving from open trades would hide the rows most worth seeing. It is deliberately not a broker position report either; that's the Executor Portfolio card, and the two disagreeing is a signal, not a bug to paper over.

The one thing that can break silently here is the close key. The tab posts `timeframe: row.tag` (`"1h"`, not `"60"`), and the server recomputes `sentKey()` from it — this works only because `timeframeTag()` is **idempotent over its own output** (`"1h"` → `"1h"`, `"1d"` → `"1d"`). If it weren't, the rebuilt key would miss the ledger and `/api/send-webhook-exit` would answer "No webhook entry recorded" rather than erroring visibly. Verified live by rebuilding the key for all four open rows from exactly what the button sends and comparing against the stored keys — all matched and resolved to a record. Re-run that check if the tag vocabulary ever changes.

Row fields prefer the stored record and fall back to the key (`rec?.symbol || parts[0]`), so a record written by a richer path keeps its fields; filter vocabularies are built from the data itself so a filter can never offer a value matching nothing; and the tab reloads on every view rather than caching, because an order can be sent from a scheduled scan or another tab and a stale view could offer Close on something already closed.

#### Closing without sending, the Type column, and history periods (2026-07-31)

A position closed **directly at the broker** had no representation here: the only close was `/api/send-webhook-exit`, which places a real order. The ledger would go on asserting a position the user no longer held — keeping its alert-quota priority, keeping the auto-close watching it, and blocking a later genuine entry on the same key (the dedupe guard keys on the entry, and an entry with no `.exit` never clears).

- **`POST /api/close-webhook-local`** records the exit and sends nothing. `recordManualClose()` in `trade_webhook.js` merges onto the same key as any other exit — so `alreadyExitSent()`, the open/closed split and `findUnclosedWebhookExits` all need no special case — stamped **`sent: false`**, the same marker the tv-alert path already uses for records it merely observed. **It deliberately does NOT require webhook credentials**: refusing to record reality because a secret is missing would leave the ledger asserting a position that no longer exists, which is the exact failure it exists to fix. It keeps the real close's "entry must be in the ledger" guard, for a different reason — there is nothing to reconcile if this system never recorded an entry, and inventing one would claim an order that was never placed. Exit side is inverted from the **stored entry** side (`buy` → `sell`), never re-derived from the strategy's current view, which can disagree. Fill price is optional and, if blank, stored as `null` rather than filled from a quote — an invented fill price reads exactly like a real one.
- **`ledgerRowType(rec)`** (in `trade_webhook.js`, next to the writers, so "sent" means one thing system-wide; served as `row.type`) is the Type column: `WH Open` / `WH Close` / `Manual Close`, plus `TV Open` / `TV Close` for the tv-alert mode that already existed in the data. The load-bearing detail: **`sent` is absent on every exit written before this shipped, and all of those were real sends, so absent must read as sent** — `exit.sent === false` is the test, never falsy.
- **History periods** (today / yesterday / WTD / MTD / last month / last 30 days / YTD / all) are a **client-side filter over already-fetched rows**, with boundaries in the **browser's local timezone** — not the ET trading-day calendar the scan/notify gates use. That is deliberate: every timestamp in the table is rendered with `toLocaleString()`, so a row displaying today's date that a "Today" filter excluded would be indefensible on screen. A row matches if **either** its entry or its close falls in the window — a position opened last week and closed this morning is part of today's activity, and filtering on the entry alone would hide exactly the close you came looking for. Week starts **Monday**. "Last 30 days" is 30 calendar days *including* today.

Verified 2026-07-31 against the real ledger (backed up and restored; two throwaway tickers, no network call): all guards refuse correctly (no `entryTime`, unknown position, missing symbol, double-close), a long records a `sell` exit and a short a `buy`, and the six real records classify as 4 `WH Open` / 2 `WH Close`. Period boundaries were checked against a fixed Wednesday with rows on each side of every edge.

#### The ledger trim could evict an OPEN position — fixed 2026-07-31

`persistSentState()` capped the ledger at 500 records by sorting every key on the entry's `at` and deleting the oldest past the cap — **with no check for whether a close had ever been recorded**. Replaying that logic against 1 old open position + 500 newer closed ones deleted the open one.

That is a money-path bug, not a display one. The ledger record IS the authorization the rest of the system runs on: an evicted open record means `dispatchExitWebhooks` no longer sees a position it opened (no automatic close, ever — and `findUnclosedWebhookExits` can't catch it either, since that also requires the record), the duplicate-send guard stops blocking a re-entry on it, and it loses alert-quota priority. Measured from the trade log, positions open at **541/month (last 30d) / 656/month (last 90d)** across the 8 timeframes, so fully armed, any position open longer than roughly four weeks would have been silently dropped. It never fired because `enabled_timeframes` has been `[]` and the live ledger holds single digits — it was latent, waiting for arming.

Two rules now govern what may leave the live ledger:
1. **An open record (no `.exit`) is never evicted, at any age.** If open positions alone exceed the cap the file simply grows — they are the working set by definition, and a bounded file is worth less than a correct one.
2. **Closed overflow is archived, never deleted** — appended to `status/webhook-sent-archive.jsonl`, and deleted from the live file *only after* the append succeeds (`archiveRecords()` returns false on a write error and the records stay put). The history view queries by period, so discarding old records would make "YTD" quietly wrong rather than visibly incomplete.

`readSentArchive()` reads them back for the history view and is **deliberately not merged into `readSentState()`** — that is the hot path every send, auto-close and alert-priority check parses, and archived records are all closed, so nothing there can need them. It returns the most recent `limit` (10,000) with `truncated`/`unreadable` counts that `/api/webhook-ledger` passes through to a `warn-box` in the tab, so a large or torn archive degrades into a *labelled* partial answer. A torn final line (crash mid-append) is skipped and counted, never thrown. `open` is filtered on `!r.exit && !r.archived` — an archived row rendering a Close button would offer to act on something already settled.

Verified: the old open position now survives (was `false`, now `true`); 22 overflow records archived oldest-closed-first with live+archive conserving all 522; 511 open positions with a 500 cap keeps all 511 and archives nothing; a torn tail yields `unreadable: 1` without throwing; `limit: 20` of 50 returns the most recent 20 and reports `truncated: true`; the endpoint merges 4 live + 3 archived into 7 correctly-typed rows with archived excluded from `open`.

### Cross-timeframe exits on webhook-held symbols (`findCrossTimeframeExits`, 2026-07-31)

User's case: DRN open on both 45m and 2h, webhook sent for the 2h leg, wanting to know when a *different* timeframe of a symbol they hold with real money exits — without adding general alert noise.

**The overlap is the norm, not an edge case.** Measured 2026-07-31: **47 of 86 open tickers were open on more than one timeframe**, and 5 of the 6 webhook-sent positions had other legs (TD alone had five: 4h/2h/3h/1h/45m). Nothing surfaced this, and nothing could have: the ledger only knows the leg it sent, and the EXIT arrives under a timeframe whose key isn't in the ledger at all, so `dispatchExitWebhooks`, `findUnclosedWebhookExits` and the level monitor all skip it by construction.

`findCrossTimeframeExits(scanResults)` indexes open ledger records by **bare ticker** (a ticker can hold several, one per timeframe) and reports any EXIT on a *different* timeframe. Same-timeframe is skipped — the existing exit paths own that case and reporting it here would double up.

**Scoping to webhook-held tickers is what makes it viable.** Unscoped it fires on every EXIT across 47 tickers. Scoped, the volume is calculable from median hold per timeframe in the trade log (45m ≈ 6.0d, 30m ≈ 3.9d, 1h ≈ 7.0d, 2h ≈ 11.8d, 3h ≈ 14.5d, 4h ≈ 22.3d): the 10 legs currently attached to 6 webhook positions produce **~34 cross-TF exits/month ≈ 8/week**.

**`relation` is the record's whole point, and it's the noise dial.** An exit on a **slower** timeframe than the one held (hold 2h, the 4h turns) means the larger trend rolled over underneath the position. An exit on a **faster** one (hold 2h, the 45m turns — the user's own DRN case) is a wiggle inside the held timeframe. Both show on the dashboard; only slower pushes to ntfy, taking ~8/week down to ~2-3. Unparseable timeframes yield `relation: null`, treated as not-slower (dashboard only) rather than guessed.

Three push gates, each removing a distinct kind of noise, in `crossTfExitNotifyLines()`:
- `relation === "slower"` (above);
- **same ET trading day, judged on the EXIT's own `exit_time`** — never the held position's entry time, which is days old by definition (the same trap already documented for `dispatchExitWebhooks`). A DOM-sourced EXIT has no `exitTime` and is therefore never pushed rather than guessed at;
- **not already pushed**, keyed `ticker|exitTf|exitTime` in `baseline.cross_tf_notified` (trimmed to 500). Without persistence a standing EXIT stays the last closed trade for days and would re-push every 15 minutes.

Wiring notes: **detection runs on every scan and is not gated on `notify`** (the dashboard half is free and must not depend on the scheduled path), inside a try/catch — the fields are additive and nothing downstream gates on them, so a failure costs a log line, never the scan. Only the push half is `notify`-gated, like the two dispatchers. `tagToResolution()` inverts `timeframeTag()` so `timeframeToMinutes` can compare a ledger tag ("45m") against a scan result's raw resolution ("45"). `/api/webhook-ledger` attaches them to open rows by `held_key` rather than the tab fetching separately — they are a property of a row, and a second fetch could resolve against a different scan than the rows were built from. Closed and archived rows never carry them.

**Detection only — nothing is closed from here.** The held leg's own strategy has *not* signalled an exit; another timeframe's has, and whether that means anything is a judgement call. It renders under the symbol on the open row so the decision and the Close / Mark-closed buttons are in one place. Same detect/surface/confirm shape as every other mutation path here.

Verified 2026-07-31 against the real 6-position ledger with synthetic scan results (no network call; the status file was backed up and restored byte-identical): 4 cross-TF exits detected from 7 inputs, correctly ignoring a same-timeframe exit, a not-held ticker and an OPEN signal; DRN 45m classified `faster` and excluded from the push while 3 slower ones pushed; a re-scan with the same exits pushed 0; a yesterday-dated exit and a null-`exitTime` exit were both shown on the dashboard and pushed 0. The endpoint attached notes to exactly the 2 intended open rows and 0 closed ones.

#### File growth: when flat files stop being the right answer

Measured 2026-07-31, so the trigger points are numbers rather than instinct.

| store | now | growth | parse cost |
|---|---|---|---|
| `trade-log/*.csv` (8 files) | 2.0 MB, 7,481 rows, 146 tickers, 2016–2026 | ~15–20 rows/day organic (~5k/yr); backfills add 2–4k in a burst | `readAllTradeLogs()` 190 ms, **uncached — re-parsed on every API call**; `buildEdgeAnalysis` 382 ms, `simulatePortfolio` 241 ms, concurrency 122 ms |
| `status/webhook-sent-state.json` | 7 records | 1 record per position; ~540–650/month if all 8 timeframes are armed | trivial; rewritten in full per write, bounded by the 500 cap |
| `status/webhook-sent-archive.jsonl` | — | the overflow above, ~2.7 MB/yr fully armed | append-only; read only by the history view |

**Postgres is the wrong tool here and adding it would be a downgrade.** The whole dataset is single-digit megabytes — three orders of magnitude below where a server-based database earns its keep — and it would put a daemon in the money path: a scheduled scan that today appends to a file would instead fail to record an order it just sent if the server weren't running. It would also cost the debugging story this project runs on (much of this file is "check `swing-signal-baseline.json` directly"); grep-ability is repeatedly how bugs here got found, including this one.

Escalation order, cheapest first — do these in order and only when the trigger fires:
1. **Memoize `readAllTradeLogs()` on file mtime** (~15 lines). Takes an Edge Analysis tab load from ~500 ms to ~0. Trigger: whenever the tab feels slow — this is the only current cost, and it is a caching problem, not a storage one.
2. **Split or archive trade-log CSVs by year** if a single file passes ~50 MB. `readAllTradeLogs` already globs `trades-*.csv`, and `archive_trade_log.js` already moves rows out, so this needs no new mechanism.
3. **SQLite (`node:sqlite`, built into the Node 24.16 already installed — no dependency, no daemon)** if either: a single analysis pass exceeds ~2 s after caching, or a query genuinely needs joins/indexes across the trade log, ledger and executor portfolio at once. It keeps the one-file, inspect-it-directly property; Postgres does not.

At the current ~5k rows/year organic, item 1 is the only one likely to matter for years.

### Missed exits are detected but never auto-dispatched (`findUnclosedWebhookExits`, 2026-07-31)

Even with arming out of the way, the automatic close can miss an exit **permanently and silently**. `notifyExitEntries` requires the EXIT to be in `changedSignals` **and** to carry an `exitTime` on the same ET trading day as the scan. Both are right for the normal case and both fail the same way: if no scan runs on the day a position exits — machine asleep, TradingView down, or an earlier long-running scan still holding the Task Scheduler slot (observed 2026-07-31: the day's first scan started 13:17 ET and ran 35+ minutes, while `UDOW` had exited at 04:00 ET) — the next day's scans see the exit as neither changed nor same-day, and no close ever goes out. The ledger goes on asserting a position the strategy closed days ago.

`findUnclosedWebhookExits(result.all_scan_results)` scans every result for an EXIT whose ledger record exists, has no `.exit`, and isn't `source: "tv-alert"`, and surfaces it as `webhook_exit_pending` → `webhookExitPending` → a warn banner in the Open Trades card with a per-row confirm-gated "Send close".

**Deliberately detection-only.** These are by definition exits the automatic path already missed, so the state behind them is stale — firing a close off multi-day-old inference could try to sell something no longer held, which is outward-facing and hard to reverse. The fresh case still closes automatically; only the stale case asks. Same detect/surface/confirm shape as the trade-log orphan banner and the strategy-identity guard. Verified against the real ledger with synthetic scan results: an unclosed EXIT is flagged, while an already-exited record, a non-EXIT row, an unknown symbol and a null entry time are all correctly ignored.
- Verified 2026-07-28 against the real ledger/module code with a throwaway fake ticker (no network call): `alreadySent`/`alreadyExitSent` transition correctly, the entry record survives a merge untouched, `exitOrderAction('LONG'/'SHORT'/'SE')` → `sell`/`buy`/`buy`, and `buildWebhookPayload`'s `action` override bypasses `orderAction(side)` correctly. Not yet verified against a real scheduled `--notify` scan end-to-end.

### The routing `tag` is editable per open position (2026-08-05)

`tag` is what the Railway executor files an order under, and it was derived from the timeframe with no way to override it. The Open Trades table's "TF" column is now a **"Tag" column holding an editable input**, defaulting to the watchlist's own timeframe (a Swing 45m position defaults to `45m`), so one signal can be routed to a group other than its timeframe's bucket without touching `rules.json`.

Four decisions that are easy to undo by accident:

- **The dedupe key does NOT move with the tag.** `sentKey()` still hashes the *timeframe's* canonical tag. The key identifies the **position**; the tag routes the **order**. Keying on an override would file the send under a key the automatic dispatch and auto-close paths — which only ever see a timeframe — can never rebuild, silently defeating both the duplicate-send guard and the "did we open this" lookup a later close depends on. This is the same class of bug as the display-vs-raw entry-time mismatch documented above, and it is covered by a test that asserts `sentKey` takes no tag at all.
- **A malformed tag is REFUSED at the endpoint, not silently defaulted.** `normalizeWebhookTag()` (`trade_webhook.js`) is the single definition of valid — `^[a-z0-9_-]{1,20}$`, trimmed and lowercased — and `buildWebhookPayload` falls back to `timeframeTag()` for anything it rejects. But `/api/send-webhook` 400s on a non-empty tag that fails it, because the user typed it to route somewhere specific and quietly filing the order elsewhere is the wrong recovery. The charset is narrow because this string is echoed into the ledger, the console log and the executor's records, where whitespace or punctuation would fragment one bucket into several.
- **A `market` payload with no override is byte-for-byte unchanged**, so the armed auto-send path (which never passes `tag`) is provably untouched — same invariant the order-type work had to preserve, and asserted by a `deepEqual` test.
- **The CLOSE reads the tag from the LEDGER, never from the request or the row.** `/api/send-webhook-exit` uses `entryRecord.tag` — the same rule as `closeAction` inverting the *recorded* entry side. A close routed under the timeframe default would ask the executor to flatten a position it never filed there.

Overrides live in **localStorage**, keyed by `bareTicker|timeframeTag|entryTimeRaw`, not on the server: it is a per-operator preference on a position that exists only until it closes, and persisting it server-side would create a second source of truth about a position the ledger already owns. The tag that actually went out is recorded by the send itself and is now shown on the row (`#swing_b`) when it differs from the default. A row with no `entryTimeRaw` renders the tag as static text — the send is already refused for that row, so an editable field would promise something unsendable.

### Manual ledger: editing an open position, and alert deletion that is recorded (2026-08-05)

Two items from `requirement.txt`. The second was already implemented (close deleted the alerts) but was **unverifiable after the fact** — the delete was fire-and-forget, so a closed row went on reading `tv_alert_status: created` with its alert ids intact whether the alerts were gone or still live.

- **`POST /api/manual-ledger/:id/update`** — `validateManualPositionUpdate(body, existing)` + `updateManualPosition(id, patch)`. **Partial by design**: only keys present in the body change, so fixing one typo cannot reset another field to a default. Two rules are checked on the **merged** row, not the patch: "at least one of stop/target" (they are the only levels the exit check and the backup alert watch, so an edit must not be able to leave a position silently unwatched), and the open-status guard, which is enforced *again* in the writer so a caller bypassing the validator cannot rewrite a closed position. An empty string clears a level; an absent key leaves it alone — the two are deliberately different.
- **`alertsAffected` decides whether the TradingView alerts are rebuilt**, and it compares merged-vs-existing rather than "was this key sent". The dashboard's Save posts the whole row, so an untouched level arrives as a no-op patch — rebuilding on that would delete and recreate a perfectly good alert on every edit. Verified live against a real position: an unchanged save returned `alertsRebuilt: false` with both real alert ids (`5297883452`/`5297883455`) still attached.
- **Rebuild order is DELETE FIRST, then create.** Creating first and deleting after leaves two live alerts on one position if the delete fails — and a stale alert firing at the *old* stop is worse than no alert, because it is indistinguishable from a real level hit. When the delete fails the row is still saved (refusing to record what you hold because TradingView is unreachable is the wrong failure) and flagged `tv_alert_status: 'stale'`, **keeping the old ids** — they are the only remaining handle on an alert still live at the previous price. Retry on a `stale` row clears them before recreating, and 502s rather than doubling up if it still cannot.
- **`markManualPositionAlertsDeleted(id, {ok})` clears the alert ids only on a CONFIRMED delete**, setting `deleted` or `delete_failed`. `alerts.deleteAlerts()` reports failure in its return value like `alerts.create()` does, so a resolved promise is not evidence the alerts are gone — anything short of `success === true` is a failure. The close endpoint returns the failure as a `warning` the dashboard shows (set *after* the reload, since `loadManualLedgerTab` clears `#ml-status` on success), instead of only reaching the console.

Verified 2026-08-05: 154/154 unit tests (12 new for update, 2 for the deletion bookkeeping, 10 for the tag), every refusal branch exercised against the live server with the real ledger left unchanged (unknown account, empty patch, clearing both levels, non-positive qty), and a notes round-trip written and reversed. **Not verified live: the actual alert rebuild path** — it deletes and recreates real TradingView alerts on a live position, so it was left for a real edit.

**Editing the entry price rescales the levels — and the rescale lives in the FORM, not the server (bug fixed 2026-08-05).** Reported symptom: changing entry price in the manual ledger left stop/target where they were and never re-synced the TradingView alerts. Root cause was that stop/target were treated as independent values, when `computeExcursionLevels` builds every level as `entry * (1 ± pct/100)` — the **percent gap is what carries meaning** and the absolute price is just where that gap landed against the old entry. `mlRescaleLevel(storedEntry, newEntry, storedLevel)` reproduces the gap exactly (`newEntry * storedLevel / storedEntry`, `round2` to match `computeExcursionLevels`), which is direction-agnostic: a SHORT's stop sits above entry and its target below, and both keep their side. Measured drift from rounding is under 0.003pp on normal prices and 0.08pp on a $3 stock.

Four things this depends on:

- **It runs in the edit form, not in `updateManualPosition`.** A server-side rescale has to either recompute behind the user's back — they confirm `144.36` and get `141.50` — or hold a second copy of a rule that already exists in `computeExcursionLevels`. Doing it in the form means what is confirmed is what is saved, the numbers are overridable in place, and **the server needs no special case at all**: the patch already carries the moved levels, so the existing `alertsAffected` → delete-then-recreate path syncs TradingView with nothing new added. A partial API PATCH of only `entry_price` therefore does *not* rescale, which is the correct reading of a partial patch.
- **A level the user has typed into is never rescaled underneath them** (`dataset.touched`) — an explicit level outranks a derived one. The add form tracks the same flag, and a fresh suggestion clears it because a re-fill is derived again.
- **Scaling is always from the STORED pair** (`defaultValue` in the row editor, `dataset.basisEntry`/`basisLevel` in the add form), never from the current values, so repeatedly editing the entry price cannot compound its own rounding.
- **The confirm dialog now spells out each move** (`Stop: 144.36 → 141.50`) and is computed from exactly the four fields the server's `alertsAffected` watches, compared the same way — so it can never promise a rebuild the server won't do, nor stay silent about one it will. A stop that moved only because the entry price was rescaled must not slip past on a generic "levels changed" line.

The **add form had the identical defect** and is fixed the same way: `mlSuggestLevels` refuses to re-suggest over a non-empty field (correctly — it must not overwrite a chosen level), so before this, changing the entry price after the levels were filled left them pointing at the old price with nothing to move them. `mlSetLevelBasis()` is called from both places that fill them — the suggestion, and the Ledger button carrying an open trade over. Verified by running the page's own `mlRescaleLevel` out of the served HTML across normal/low/high prices, a SHORT, an unchanged entry, and six unusable inputs (all → `null`, i.e. the caller keeps the stored value rather than writing `NaN`). Note the dashboard HTML is `readFileSync` per request, so this half needs only a browser refresh, not a server restart.

### `accounts.json` carries equity + alloc %, and the add form auto-sizes Qty (2026-08-05)

`accounts.json` was a flat list of names. Each entry may now instead be an object carrying `equity` and `alloc_pct`, and picking that account in the Manual Ledger's Add-entry form fills Qty with `floor(equity × alloc_pct / 100 / entry price)`. `src/core/accounts.js` (`normalizeAccounts`, `allocationQty`, `allocationNotional`) owns both shapes; `/api/accounts` returns `{accounts: names[], details: [...], warnings: []}`.

- **`accounts` stays a bare string list and both save-time guards compare against `.names`.** This is the load-bearing detail: the two "is this a known account" checks in `serve_signal_status.js` did `cfg.accounts.includes(name)` against the raw array, which rejects **every** object-form account — the whole Manual Ledger would refuse to save. Confirmed live before the fix: the old server, reading an object-form file, served `accounts: []` (its filter was `typeof a === 'string'`), i.e. an empty picklist. Any new reader of this file must go through `normalizeAccounts`, never `cfg.accounts` directly.
- **Nothing is ever defaulted.** A missing `equity` is not 0 and a missing `alloc_pct` is not 100% — either substitution sizes a real position off a number nobody entered. Half-configured is not an error either: the account is still offered, it just doesn't auto-size. Same reasoning as the `scanned_at` entry-time fallback documented above — an unknown must surface as unknown.
- **`alloc_pct > 100` is refused as a typo, with a warning, not honoured as margin.** It is a share of the account, so an extra digit is far likelier than a deliberate 5× instruction, and honouring it would size several times the account. Split across accounts instead. Every dropped or ignored entry (bad equity, duplicate name, nameless row) comes back in `warnings` and renders in a warn-box — an account that quietly stops auto-sizing is indistinguishable from one that was never configured.
- **Qty auto-fill never writes 0 and never overwrites a hand-typed value.** `positive(qty)` on the server rejects 0, so writing it would make an unsubmittable form with no explanation; the field is left blank and the note says the allocation can't cover one share at that price. `dataset.touched` (the same convention the stop/target rescale uses) protects a typed Qty; clearing the field releases it back to auto but deliberately does **not** refill on the spot, or the next keystroke would append to a number just deleted.
- **`allocationQty` is duplicated as `mlAllocQty` in the dashboard, on purpose, and a test pins them together.** The form re-sizes on every entry-price keystroke, which a round trip can't keep up with — same reasoning as `mlRescaleLevel` living in the form. `tests/accounts.test.js` extracts the page's own copy out of the served HTML and cross-checks it against the module over 19 input rows, so the pair cannot drift silently. Change both together.
- **The row editor deliberately does NOT auto-size.** An open row's Qty is a record of what was actually filled; recomputing it because the account or entry price was edited would rewrite a fact. Levels are derived and get rescaled; Qty is observed and does not.
- **The floor uses `toFixed(10)` before `Math.floor`.** `(50000 × 10) / 100 / 5` is exactly 1000 shares in decimal and can land a hair under in binary — a bare floor hands back 999.

Verified 2026-08-05: 174 unit tests (20 new, was 154); live `/api/accounts` against a mixed real config returning a sized account, a `alloc_pct: 150` account correctly degraded with its warning, and a bare-string account; the save-time guard accepting both entry forms and rejecting an unknown account with a real 400; and `mlAutoQty` run out of the served HTML under a DOM stub across 8 states (sized, re-priced, no price, unsized account, no account, allocation under one share, and a hand-typed Qty on both a sized and an unsized account). Note the server half needs a restart to take effect (`accounts.json` itself is read fresh per request); the dashboard half needs only a browser refresh.

### Capacity Sweep pivots on expectancy now, and Sim Templates carry a decision forward (2026-08-05)

Two halves of one request: rank the Capacity Sweep on expectancy and avg win/loss rather than CAGR/DD, then be able to **save a chosen combo** and have every position and order opened under it say so.

**The sweep's pivot is now a selectable view control, defaulting to expectancy.** `sweepMaxPositions()` carries `expectancyPct` (= `expectancyPctOfEquity`, the size-neutral form), `expectancyUsd`, `avgWinUsd`, `avgLossUsd` and `winLossRatio`; the dashboard's `PS_PIVOTS` map drives the ★, the bar chart and a tinted winning column. Four decisions in it:

- **`expectancyPct`, never `expectancyUsd`, is the default.** Position size is `equity / slots`, so the dollar figure rises with slot count purely because the account compounds — it would rank slot counts by their size divisor. The percent form scores each trade against the equity that funded it (see the `expectedPct` fix above, which is where that field came from).
- **`winLossRatio` uses `Math.abs(avgLossUsd)`** — `simulatePortfolio` returns that field **negative**, the same trap `paper_run.js` already hit once. Null rather than `Infinity` when nothing lost, so an unlossed row renders `—` instead of sorting above every real one.
- **CAGR/DD is kept, not demoted on principle.** The "ranks worse than random" finding is about ranking *individual symbols on a dozen trades*; this is a whole-portfolio equity path, which is the case that section explicitly exempts. Switching the pivot moves the ★ only — every column shows for every metric, so a ranking never hides the trade-off it costs.
- **Bar widths are guarded against a zero denominator**, because `NaN%` renders as a **full-width** bar — i.e. an unscored slot count would display as the best performer. Same bug class already fixed once in the Sweet Spot matched-window card, and the `best` reducer likewise only considers scored rows rather than treating null as `-Infinity`.

**`src/core/sim_templates.js` stores the chosen combo.** New `sim_templates` table (timeframes, slots, universe/tickers, exit-rule variant, capital, account, notes, KPI snapshot, created date), a `template_id` column on `manual_positions`, a Sim Templates tab, a "Save as Sim Template" button under the Capacity Sweep, and a picker in the Manual Ledger's add form and row editor.

- **It lives in the manual-ledger SQLite file via `registerLedgerSchema()`/`getLedgerDb()`, not its own database.** Two `DatabaseSync` connections to one file from one process can collide on write locks, and a separate file would put template rows out of reach of the ledger join. Registration happens at import time and is re-applied if the connection is already open, so import order is not load-bearing.
- **`short_desc` (≤10 chars) is an IDENTIFIER, not a label** — it goes out in real webhook payloads and is what a human reads off a fill. Charset-restricted to `[a-z0-9_-]` and **UNIQUE**, enforced by the index rather than a racy read-then-write. Malformed input is **refused, never stripped**: stripping would silently produce a different identifier than the one typed, riding along on real orders. `suggestShortDesc()` drops whole timeframe segments rather than truncating mid-way, because `15m3` from `15m+30m` reads as a timeframe that was never selected — and it is a form pre-fill only, never a fallback on save.
- **The KPI snapshot is stored verbatim and is NEVER recomputed** — not on read, and `validateTemplateUpdate` ignores a `kpis` key outright. The trade log grows continuously, so recomputing would leave the template agreeing with today's data and disagreeing with the decision it recorded. Drift is *reported* (`templateStaleness`, ≥50 new trades, the same threshold the Sweet Spot tab uses) and never repaired. Non-finite and unrecognised KPIs are dropped rather than stored: a stored `Infinity` renders as a real number and sorts above every honest row.
- **The snapshot is taken from the SWEEP ROW at the chosen slot count**, not from the headline metrics — the sweep row is what the ★ and the pivot ranked, so the template records the numbers actually being compared. No exact row ⇒ nearest row, with a warn box naming which one it used.
- **Templates are ARCHIVED, never deleted.** The id is stamped on ledger rows and on records at the executor; deleting would strand every one of them, destroying the attribution precisely for the configurations that stopped being used. Archived templates drop out of the pickers and out of auto-dispatch resolution but still resolve by id and by `short_desc`, and the row editor always offers a position's *own* template even when archived, so opening the editor cannot silently detach it.
- **The account link lives on the TEMPLATE, so `accounts.json` stays a hand-edited config the dashboard never writes.** One account can hold several templates; a template names at most one, validated against `normalizeAccounts().names` exactly as the ledger's own save does.

**Payload attribution — two string fields, `template_id` and `template`, and only when a template is resolved.** A market payload with no template stays **byte-for-byte** what it was before this shipped (asserted by a `deepEqual` test), because the armed auto-send path is live money and the executor's tolerance for unrecognised keys is undocumented — an untagged order must never be what discovers it is intolerant. Deliberately **not** folded into `tag`, which selects the executor's strategy group; doing so would fragment one routing bucket into one per template.

- **Automatic dispatch resolves EXACT-ONE-MATCH among active templates and otherwise attaches nothing.** Two templates claiming one timeframe is legal (two accounts can both trade 15m) but there is no basis to choose, and a wrong template id on a real order is worse than none. `findTimeframeCollisions()` surfaces every contested timeframe in the tab so this is a *visible* stop, not a silent one. The template set is read **once per dispatch**, not per event, so it cannot change mid-batch and attribute two signals from one scan to different configurations.
- **Every CLOSE reads the template off the LEDGER RECORD, never re-resolved** — same rule `closeAction` and `tag` already follow. Re-resolving would let a template edited or archived since the entry attribute the close to a different configuration than the position was opened under.
- **A `template_id` that does not resolve is REFUSED (400), never dropped**, on both the send and the manual-ledger paths. The user picked it to attribute the order; sending an unattributed one instead is silent data loss on the money path. An **archived** template is still accepted — archiving retires a config from new entries, it does not invalidate positions held under it. `''` on the ledger's partial update is a deliberate *detach*, distinct from omitting the key.

Verified 2026-08-05: 42 new unit tests (`tests/sim_templates.test.js`, wired into `test:unit`/`test:all`), 203 unit tests green overall. ### TradingView price-alert create/delete — the real request schema (reverse-engineered)

`pricealerts.tradingview.com/create_alert` looks like a normal REST endpoint (it returns structured JSON, not a CORS failure, for almost any request body), which made a wrong payload shape look like an auth/transport problem for a long time. It is neither — it's a plain HTTPS POST from the page's own `fetch()`, not a WebSocket RPC (a private pub/sub WS channel does carry the resulting `alerts_created`/`alerts_updated` broadcast, which is a red herring if you go looking for the create request there instead). The real schema, captured 2026-07-23 via CDP `Network.requestWillBeSent` while manually creating+deleting one alert in the **Desktop app** (the CDP session only attaches to that target — testing in the TradingView web browser instead produces total silence, no events at all):

- **Create**: `POST https://pricealerts.tradingview.com/create_alert` — no query params needed. `Content-Type: text/plain;charset=UTF-8` (required — `application/json` triggers a CORS preflight the server rejects outright as "Failed to fetch"; `text/plain` is a simple request and skips preflight while the body is still parsed as JSON server-side). Body:
  ```json
  {"payload": {
    "conditions": [{"type": "cross", "frequency": "on_first_fire",
      "series": [{"type": "barset"}, {"type": "value", "value": 162.76}], "resolution": "1"}],
    "symbol": "={\"adjustment\":\"splits\",\"currency-id\":\"USD\",\"session\":\"extended\",\"symbol\":\"BATS:FAS\"}",
    "resolution": "1", "message": "...", "sound_file": "alert/fired", "sound_duration": 3,
    "popup": true, "auto_deactivate": true, "email": true, "sms_over_email": false,
    "mobile_push": true, "web_hook": null, "name": null, "expiration": "<ISO, ~30d out>",
    "active": true, "ignore_warnings": true
  }}
  ```
  Two things about this are non-obvious and are exactly what the old broken payload got wrong: (1) it's `{"payload": {...conditions array...}}`, not a flat `{type, value}` pair; (2) the encoded-symbol string needs a `session` key — the code that builds it was silently omitting one, and the server accepts the malformed symbol string without complaint but then rejects the whole request as `{"s":"error","err":{"code":"invalid_request"}}` with no indication which field was the problem. Response on success: `{"s":"ok","id":"...","r":{...,"alert_id":<number>,...}}` — `r.alert_id` is the real numeric id, needed for deletion later.
- **Delete**: `POST https://pricealerts.tradingview.com/delete_alerts`, same content-type, body `{"payload":{"alert_ids":[<number>,...]}}`. Response `{"s":"ok","r":null}`.
- Only the `"cross"` condition type is verified live (it fires once regardless of which direction price approaches from, which is exactly what a stop/target level alert wants). `toConditionType()` in `src/core/alerts.js` maps `greater_than`/`less_than` to `"greater"`/`"less"` as a best-effort guess based on TradingView's known alert vocabulary — **unconfirmed**, don't trust it without testing if a caller ever actually needs a one-directional condition.
- `alerts.list()`'s active-count filter (used by `createExcursionAlerts`'s `MAX_ALERTS` quota gate) already filters on `a.active` — long-expired/inactive manual alerts from months earlier don't count against the quota, only genuinely active ones do. Don't "fix" a seemingly-tight quota by raising `MAX_ALERTS` before checking `alerts.list()` output for this distinction.
- `morning.js`'s `drainPendingAlertCleanup()` drains `baseline.pending_alert_cleanup` (populated by `processLevelViolationsAndCleanup` when a trade's signal reads EXIT) by calling `alerts.deleteAlerts({ alert_ids })` for each queued batch — entries that fail to delete stay queued and retry on the next scan rather than being dropped.
