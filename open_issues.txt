ISSUE 1: Ranking open signals for a max-15-position portfolio
================================================================================
STATUS: Implemented.

Request:
  "if i want to have a max of 15 pos portfolio, what is the best method to
  select a good signal. if there is a measure that can be applied among all the
  open signal in a given tf, can we add a column to rank it so that i can avoid
  buying a weak pos" - with a TradingView Key Stats screenshot (Sharpe ratio,
  expected payoff, average PnL, winners %, avg profit / avg loss, largest
  profit / largest loss) offered as candidate KPIs.

What was done:
  New "Edge" column on the Open Trades table = the symbol's EXPECTANCY
  PERCENTILE WITHIN ITS OWN TIMEFRAME, 0-100, computed from the closed-trade
  log by buildSymbolEdgeScores() in src/core/edge_analysis.js.

  Of the KPIs in the screenshot, only "Expected payoff" (= expectancy) is used
  in the score. The others are shown in the cell's hover tooltip as diagnostics
  only. This is not a style preference - it was measured on this data
  (walk-forward, rank on each symbol's first half, score the second half,
  Spearman rho): expectancy +0.381, totalReturn +0.225, cagr +0.092,
  winRate -0.018, sharpe -0.133, cagrDd -0.145, profitFactor -0.168. The ratio
  metrics rank slightly WORSE THAN RANDOM out-of-sample, because max drawdown /
  worst loss over ~12 trades is essentially one unlucky trade, which
  mean-reverts. Percentile rather than the raw value because expectancy scales
  hard with timeframe (15m ~1.7%/trade vs 4H ~7%), so a raw ranking is really a
  timeframe ranking.

  A "Max positions" box (default 15, stored in the browser) pools every open
  position across all timeframes by Edge score and flags the ones ranked below
  the cap as over-cap / liquidation candidates. Percentile is what makes that
  cross-timeframe pooling legitimate.

  Symbols with under 8 closed trades (or fewer than 4 ranked peers on the
  timeframe) show "n/a" and are NEVER flagged over-cap - "not enough history to
  judge" must not read as "weak".

Answer to "what is the best method":
  Rank by Edge (expectancy percentile) and use it as a FILTER, not a priority
  order. Measured: reordering which signal to take when several fire barely
  moved anything (simultaneous signals are rare), but dropping the bottom half
  by past expectancy moved a lot - and only when capacity-constrained. At 5
  slots it helped in 5 of 5 split points; at 10 slots only 3 of 5, twice
  materially negative. A 15-slot cap against ~135 currently-open positions is
  roughly 11% of the book, deep in the regime where selection pays.
  Do NOT screen by drawdown or any ratio metric - tested and rejected
  2026-07-25, it inverts on expectancy and loses on both CAGR and portfolio
  drawdown.

Verify by:
  Open Trades card -> Edge column populated, hover for expectancy / win rate /
  payoff / trade count. Set Max positions and confirm the over-cap flags and
  the "N over cap - weakest: ..." summary change with it.

ISSUE 2: Org / New rank columns, to liquidate a weak position for a new one
================================================================================
STATUS: Implemented.

Request:
  "as the new open pos are added to the tf, add two columns - org, new so that
  if i want i can liquidate a weak pos to make room for new if needed."

What was done:
  Two rank columns per row, both by Edge, both within the row's own timeframe:
    Org - rank among the positions that were ALREADY open before today's new
          arrivals. Reads "new" on a position opened today (it wasn't in that
          book), and "-" if ranking hasn't run for the snapshot at all.
    New - rank among every position now open on that timeframe, today's
          entries included, plus a drift arrow when the two disagree.
  attachOpenTradeRanks() in edge_analysis.js; "new" = same ET trading day, the
  same calendar test the notify/webhook gates already use.

  One rank alone can't show displacement - the ranks only move because the set
  changed, which is exactly the event being asked about.

Verified live:
  Swing 45m read LFST 1/10 -> 1/14 (held), TEX arriving today at new -> 3/14,
  pushing OII 3/10 -> 4/14. 23 of 135 open positions were same-day entries.

Verify by:
  Open Trades -> a timeframe with same-day entries shows Org "new" on those
  rows and a red down-arrow on whatever they displaced.

ISSUE 3: Webhook only sent plain market buys - full order_type / time_in_force
================================================================================
STATUS: Implemented for the manual (human-confirmed) paths. Automatic dispatch
        deliberately unchanged.

Request:
  Support the executor's documented contract: order_type of market / limit /
  stop / stop_limit / trailing_stop with the required limit_price, stop_price,
  trail_percent or trail_price; time_in_force of day / gtc / opg / cls / ioc /
  fok; opg and cls only valid on market or limit; trailing_stop forces gtc.

What was done:
  validateOrderSpec() in src/core/trade_webhook.js is the single definition of
  "valid", shared by the dashboard form and RE-RUN server-side on every send -
  a priced type without its price is a hard HTTP 400 at the executor, and a
  wrong-but-accepted order is the failure worth preventing. 0 counts as
  missing, not as a price.

  buildWebhookPayload() now emits limit_price / stop_price / trail_percent /
  trail_price / time_in_force as required. A market order still emits the
  original payload byte-for-byte (no order_type key at all), so nothing about
  the existing armed path changes.

  Also fixed here: the limit support added earlier the same day sent only
  `price` and never `limit_price`, which the executor rejects with a 400. It had
  never actually been used, so nothing was mis-sent.

  New manual CLOSE button on any position whose ENTRY is in the webhook ledger,
  with the same order form -> POST /api/send-webhook-exit. This is the
  slot-freeing action for Issue 2. Scoped exactly like the existing auto-exit:
  it refuses to close a position the executor was never told about, and the
  closing side is the inverse of the RECORDED entry side, not a re-derivation.

  Entry rows also now carry the real LONG/SHORT side - previously absent, so a
  manual send always defaulted to buy.

Verified live (nothing was sent - every case was refused before the fetch):
  limit without price -> refused; opg on a trailing stop -> refused; bogus type
  and bogus tif -> refused; close on a position with no ledger entry -> refused;
  close without an entry time -> refused. All 8 valid payload shapes inspected.

Verify by:
  Open Trades -> Trade Webhook cell. Pick Limit and confirm the price box
  appears and Send is refused without one. On an already-sent row, confirm a
  Close control appears and the confirm dialog says CLOSE.

NOT DONE / still open:
  - The automatic paths (scheduled dispatchTradeWebhooks / dispatchExitWebhooks)
    still always send a plain market order with no TIF. Deliberate: there is no
    human present in those paths to choose a type or a price. If auto-limit is
    ever wanted, the blocker is that bid/ask are not available from a normal
    scan - quote_get returned no bid/ask fields, confirmed live, because
    getQuote()'s bid/ask come from a DOM scrape of a panel that isn't in this
    chart layout.
  - The Edge score is history-based and does not look at the position's live
    P&L. That is on purpose: cutting positions that are currently down was
    tested (Stop Loss variant, and the oracle-eviction upper bound) and loses,
    because longs recover a long way from their worst point on average.
